# Сервис сезонного лидерборда

PostgreSQL как source of truth, transactional outbox, Redis Sorted Set как read model.
Проектное решение и его обоснование — в [docs/RFC-001-leaderboard.md](docs/RFC-001-leaderboard.md).

```
POST /score ──▶ PostgreSQL ──▶ outbox worker ──▶ Redis ZSET ◀── GET /leaderboard/top
             (UPSERT + outbox   (Lua apply,        leaderboard:{season}   GET /leaderboard/rank/{id}
              в одной tx)        водяной знак)
```

## Запуск

Нужен Docker. Одна команда поднимает всё: PostgreSQL 17, Redis 7 (AOF everysec, noeviction), миграции (one-shot `migrate`), API и outbox worker.

```bash
docker compose up --build
```

Порты на хосте по умолчанию: API `3000`, метрики воркера `9100`, PostgreSQL `5433`, Redis `6380`. Если порт занят (например, на `5433` уже слушает локальный PostgreSQL), переопредели переменную — её читают и compose, и приложение, и тесты:

```bash
POSTGRES_PORT=15433 docker compose up --build
```

Переменные: `POSTGRES_PORT`, `REDIS_PORT`, `API_PORT`, `METRICS_PORT` — см. [.env.example](.env.example). Значения можно положить в `.env`: compose читает его сам. Если задан `DATABASE_URL` или `REDIS_URL`, они важнее.

Локальная разработка (нужен Node 22): хранилища в Docker, API и воркер нативно.

```bash
npm install
docker compose up -d postgres redis
npm run migrate                       # схема + сезон текущего месяца
npm run dev:api                       # API на :3000
npm run dev:worker                    # outbox worker (в другом терминале)
POSTGRES_PORT=15433 npm test          # тесты; порт — тот же, что у compose
```

Проверка:

```bash
curl -s -X POST localhost:3000/score -H 'content-type: application/json' \
     -d '{"player_id":"alice","score_delta":100}'
# {"player_id":"alice","season_id":202609,"score":100}
curl -s 'localhost:3000/leaderboard/top?limit=10'
curl -s 'localhost:3000/leaderboard/rank/alice?n=5'
curl -s localhost:9100/metrics          # backlog и лаг outbox
```

Команды:

| Команда | Что делает |
|---|---|
| `npm run migrate` | применяет `migrations/*.sql` (forward-only, под advisory lock) |
| `npm run create-season -- 202610` | создаёт сезон, его партицию и строку `worker_state` заранее |
| `npm run rebuild-leaderboard -- [--season 202609] [--force]` | восстанавливает Redis из PostgreSQL |
| `npm run seed -- --players 1000000` | заливает игроков через `COPY`, продвигает `tie_seq`, делает `rebuild --force` |
| `npm test` | интеграционные тесты (нужны поднятые `postgres` и `redis`, БД `leaderboard_test` создаётся автоматически) |
| `npm run k6:write` / `k6:read` / `k6:mixed` | нагрузочные сценарии через `grafana/k6` в Docker |

Конфигурация через переменные окружения — см. [.env.example](.env.example).

## API

| Метод | Ответ |
|---|---|
| `POST /score` `{"player_id","score_delta"}` | `200 {"player_id","season_id","score"}` — новый абсолютный счёт из PostgreSQL. `400` валидация (пустой id, `score_delta = 0`, не целое), `422` счёт вне диапазона, `503` нет активного сезона или PG недоступен. |
| `GET /leaderboard/top?limit=100` | `{"season_id","entries":[{"rank","player_id","score"}]}`. `limit` 1..1000. |
| `GET /leaderboard/rank/{player_id}?n=5` | `{"season_id","player":{…},"above":[…],"below":[…]}`. `n` 0..50. `404`, если игрока нет в рейтинге. |
| `GET /health` | liveness: `200 {"status":"ok"}`, хранилища не проверяет — падение PG или Redis не должно перезапускать API. |
| `GET /ready` | readiness: `200` / `503` с состоянием PG и Redis. |

Сортировка: по убыванию очков, при равенстве выше тот, кто раньше получил этот счёт. Позиции с 1, без дублей.

`POST /score` возвращает счёт сразу, а `/top` и `/rank` отстают на лаг воркера (десятки миллисекунд, см. измерения ниже).

## Как это устроено

**Запись.** Один SQL-запрос в одной транзакции: `INSERT … ON CONFLICT DO UPDATE SET score = score + delta, tie_seq = nextval()` и `INSERT INTO leaderboard_outbox` с абсолютным состоянием. Сезон выбирается по времени БД. Конкурентные обновления сериализуются блокировкой строки в `ON CONFLICT`, lost update невозможен (тест: 200 параллельных `+1` дают ровно 200).

**Tie-break в Redis.** Sorted Set при равном score сортирует по имени, поэтому порядок закодирован в сам score: `score * 2^32 + (2^32 - 1 - tie_local)`, где `tie_local = tie_seq - season.tie_base`. Всё < 2^53, double точен. Отсюда ограничения: `|score| < 2^21` (CHECK в таблице) и до 2^32 обновлений за сезон.

**Воркер.** Один активный экземпляр (leader lock в PG), резервный ждёт. Цикл: `SELECT … FOR UPDATE SKIP LOCKED` пачки до 500 событий, схлопывание по игроку, один Lua-вызов на сезон, `DELETE` и `COMMIT`. Lua-скрипт применяет событие, только если его `tie_local` новее сохранённого: повторы и перестановки безопасны.

**Водяной знак.** Каждая пачка получает номер из последовательности. Redis хранит максимальный применённый номер в `leaderboard:{season}:meta`, PG — последний закоммиченный в `worker_state`. Если `meta.batch < last_batch`, Redis потерял хвост AOF (или это отстающая реплика), и воркер запускает rebuild. Плановый рестарт Redis с целым AOF rebuild не вызывает. `FLUSHALL` ловится по отсутствию `meta`.

**Rebuild.** Берёт эксклюзивный advisory lock (воркер держит shared на каждую пачку, поэтому гонки с незавершённой пачкой нет), читает партицию keyset-пагинацией, заливает во временный ключ, атомарно `RENAME` + `HSET meta` одним Lua-скриптом, затем поднимает водяной знак в PG. Читатели во время rebuild видят старый ключ, а не половину нового.

**Сезоны.** `player_scores` партиционирована по `season_id`, у каждого сезона свой ключ Redis. Процедура смены — в разделе «Смена сезона».

Подробности, доказательство корректности водяного знака и разбор отказов — в RFC, разделы 3.3 (отказы и восстановление) и 4.4 (водяной знак, пересборка).

## Смена сезона

Сезон — строка в `seasons` с границами `[starts_at, ends_at)`, партиция `player_scores_<id>`, строка `worker_state` и ключи Redis `leaderboard:{<id>}` и `leaderboard:{<id>}:meta`. Сезон записи определяет время транзакции в PostgreSQL, код API и воркера при смене сезона ничего не делает. Автоматического планировщика в задании нет: шаги ниже выполняются вручную; в production — плановой задачей (Kubernetes CronJob или pg_partman).

**1. Создать следующий сезон заранее** — за несколько дней до конца текущего. Кто: CronJob раз в сутки (идемпотентно: «создать, если нет») или оператор.

```bash
npm run create-season -- 202610            # границы по умолчанию: календарный месяц UTC
# или с явными границами:
npm run create-season -- 202610 2026-10-01T00:00:00Z 2026-11-01T00:00:00Z
```

`create_season()` в одной транзакции вставляет строку сезона с `tie_base = nextval('tie_seq')`, создаёт партицию и строку `worker_state`. Сезоны не могут пересекаться (`EXCLUDE`), повторное создание того же id — ошибка. Первый сезон создаёт миграция `002_initial_season.sql` (текущий месяц).

**2. Граница сезона** — ничего запускать не нужно:

- `POST /score` после `ends_at` пишет в новую партицию, событие outbox несёт новый `season_id`;
- воркер доставляет события в новый ключ; `meta` нового сезона создаётся первой же пачкой (`expected = 0`), пересборка не нужна (тест `a new season bootstraps its meta without a rebuild`);
- события старого сезона, закоммиченные до границы, но ещё лежащие в outbox, доставляются в старый ключ;
- `/top` и `/rank` до 1 с (TTL кеша сезона) показывают старый сезон, затем новый — в начале сезона рейтинг пуст и заполняется по мере начислений;
- `tie_local` нового сезона считается от его `tie_base`, поэтому лимит 2^32 обновлений действует на каждый сезон отдельно.

**Если следующий сезон не создан**, после `ends_at` активного сезона нет: `POST /score` отвечает `503 {"error":"no_active_season"}` и начисление **не сохраняется** — клиент должен повторить после создания сезона; `/top` и `/rank` тоже отвечают `503`. Восстановление — шаг 1, перезапуск сервисов не нужен. Поэтому в production нужен алерт «на следующий месяц нет сезона».

**3. Архивировать старый сезон** — после границы, когда поздние события доставлены. Кто: оператор или та же плановая задача. Проверено на PostgreSQL 17.

```sql
-- a) outbox старого сезона пуст (иначе подождать воркер)
SELECT count(*) FROM leaderboard_outbox WHERE season_id = 202609;

-- b) итоговая таблица в порядке рейтинга (тот же порядок, что в Redis: очки, затем tie_seq)
\copy (SELECT row_number() OVER (ORDER BY score DESC, tie_seq) AS rank, player_id, score FROM player_scores_202609 ORDER BY score DESC, tie_seq) TO 'season_202609.csv' WITH CSV HEADER

-- c) отсоединить партицию; CONCURRENTLY не блокирует запись в текущий сезон
ALTER TABLE player_scores DETACH PARTITION player_scores_202609 CONCURRENTLY;
```

```bash
# d) выгрузить отсоединённую таблицу в холодное хранилище и удалить её
pg_dump -t player_scores_202609 -Fc leaderboard > player_scores_202609.dump
psql leaderboard -c 'DROP TABLE player_scores_202609'
```

Строки `seasons` и `worker_state` старого сезона можно оставить: это история границ сезонов, а проверка водяного знака смотрит только сезоны с `ends_at > now()`.

**4. Удалить ключи Redis** после периода хранения (например, 7 дней для разбора обращений). API читает только активный сезон, поэтому для пользователей ключ после границы уже не нужен.

```bash
redis-cli UNLINK 'leaderboard:{202609}' 'leaderboard:{202609}:meta'
```

`UNLINK` освобождает память в фоновом потоке и не блокирует Redis, в отличие от `DEL` на ключе с миллионами элементов.

Не запускайте `rebuild-leaderboard --season <старый>` после `DETACH`: партиция уже не видна через `player_scores`, пересборка получит 0 строк и заменит ключ пустым.

## Почему именно так

Сравнение вариантов по критериям задания. N — число игроков сезона (до 10 млн), M — размер ответа (limit или 2n+1). Где не указано иное — асимптотика и качественная оценка, а не замер: измерялся только выбранный вариант, его цифры — в разделе «Результаты нагрузочных тестов».

| Критерий | A. Только PostgreSQL | B. Только Redis (AOF) | C. PG + Redis, dual write | **D. PG + outbox + Redis (выбран)** | E. PG + CDC (Debezium) + Redis |
|---|---|---|---|---|---|
| **Консистентность** | строгая: чтение видит свою запись | строгая | нет гарантии: сбой между коммитом в PG и `ZADD` оставляет Redis расходящимся навсегда | eventual: чтения отстают на лаг воркера, но всегда сходятся к PG | eventual, как D |
| **Надёжность записи** | подтверждённое не теряется | `appendfsync everysec`: при падении теряется до ~1 с подтверждённых записей; `always` — надёжно, но fsync на каждую запись | в PG не теряется, в Redis может потеряться | подтверждённое не теряется: счёт и событие в одной транзакции PG | как D |
| **Чтение top при 10 млн** | O(log N + M) по индексу `(season, score DESC, tie_seq)` — дёшево | O(log N + M), `ZRANGE … REV` | O(log N + M) | O(log N + M) | O(log N + M) |
| **Чтение rank при 10 млн** | `COUNT(*)` строк выше игрока — O(позиция): для середины рейтинга ~5 млн записей индекса на один запрос, при тысячах rank/с не выдерживает | O(log N), `ZREVRANK` | O(log N) | O(log N), позиция и соседи одним Lua-скриптом | O(log N) |
| **Запись** | один UPSERT, но индекс по `score` меняется при каждом начислении: нет HOT update, больше WAL и bloat | Lua read-modify-write, O(log N), в памяти | UPSERT + синхронный вызов Redis в запросе: задержка обоих хранилищ, при недоступном Redis — ошибка или пропуск | UPSERT + INSERT в outbox в одной транзакции; Redis в пути записи не участвует | один UPSERT, изменения читаются из WAL |
| **Восстановление** | не требуется, стандартные бэкапы и реплики PG | только из AOF/RDB; потерянное не восстановить, истории прошлых сезонов нет | ручная сверка; неизвестно, когда Redis разошёлся | автоматическое: водяной знак обнаруживает потерю в Redis, пересборка из PG за O(N) | пересборка из PG или перечитывание с позиции слота |
| **Сложность эксплуатации** | низкая: одно хранилище | низкая по числу компонентов, но весь рейтинг в памяти, настройки persistence критичны | низкая на старте, хрупкая в сбоях | средняя: воркер (один активный), очистка outbox и autovacuum, мониторинг backlog | высокая: Kafka Connect/Debezium, слоты репликации (при остановке потребителя копится WAL) |
| **Главный недостаток** | rank не масштабируется | нет source of truth | тихая порча рейтинга | лаг чтений и лишний процесс | лишняя инфраструктура для задания |

**Выбран D** — самый простой вариант, который одновременно даёт O(log N) для rank, не теряет подтверждённые записи и сам сходится после частичных сбоев. Цена — отставание чтений на время доставки и один дополнительный процесс.

## Тесты

`npm test` — 40 тестов, vitest, против реальных PostgreSQL и Redis:

- конкурентное накопление, валидация, `422` при переполнении, `503` без сезона;
- tie-break: раньше набравший выше; изменивший счёт опускается среди равных;
- Lua apply: идемпотентность, старое не перезаписывает новое, отрицательные счета, бутстрап нового сезона, `STALE`/`NOMETA`;
- воркер: доставка и водяной знак, недоступный Redis (события остаются в outbox), падение между apply и commit;
- rebuild: тот же порядок, что у штатной доставки; пропуск при целом водяном знаке; восстановление после `STALE` и `NOMETA`; seed в обход outbox; блокировка воркера на время rebuild;
- API: top, rank с соседями и обрезкой у краёв, `404`, лаг между POST и чтением; `/health` не зависит от хранилищ, `/ready` — зависит;
- недоступный PostgreSQL (TCP-прокси обрывает соединения): `/top` и `/rank` отвечают из Redis, `POST /score` — `503` и снова `200` после восстановления без рестарта процесса; `/health` — `200`, `/ready` — `503`; без кешированного сезона — `503`, не `500`.

## Проверка перезапусков (ручная процедура)

Цель: убедиться, что данные и порядок рейтинга переживают перезапуск каждого компонента. Проверка выполнена 2026-09-17 на Mac (Apple M2 Pro), Docker 27.4.0, Compose 2.31.0, на чистом стеке под отдельным именем проекта, чтобы не задеть рабочие volumes:

```bash
export POSTGRES_PORT=15434 REDIS_PORT=16380 API_PORT=13000 METRICS_PORT=19100
docker compose -p lb-clean up -d --build --wait     # чистые volumes lb-clean_*
# 6 начислений: alice 100, bob 100, carol 50, dave 70, alice +20, carol +50
curl -s -X POST localhost:13000/score -H 'content-type: application/json' -d '{"player_id":"alice","score_delta":100}'
# ... остальные аналогично
# снимок: дождаться outbox_backlog 0 на :19100/metrics, затем
curl -s 'localhost:13000/leaderboard/top?limit=10'; curl -s 'localhost:13000/leaderboard/rank/bob?n=2'
# по очереди: restart → дождаться /ready 200 → backlog 0 → снимок → сравнить с исходным
docker compose -p lb-clean restart redis
# во время рестарта postgres — фоновый цикл curl по /top и /rank каждые 100 мс,
# после — POST /score с повтором до 200; RestartCount снимается сразу после
docker inspect lb-clean-api-1 lb-clean-worker-1 --format '{{.Name}} RestartCount={{.RestartCount}}'
docker compose -p lb-clean restart postgres
docker compose -p lb-clean restart api
docker compose -p lb-clean restart worker
docker compose -p lb-clean down -v
```

Результат:

| Перезапуск | top и rank после | Что происходило |
|---|---|---|
| исходно | `alice 120, bob 100, carol 100, dave 70` | bob и carol по 100: bob выше, он получил 100 раньше |
| `redis` | совпадают с исходными | AOF цел, водяной знак сошёлся, `worker_rebuilds_total 0` |
| `postgres` | совпадают с исходными | API и воркер **не падали** (`RestartCount=0`). Чтения во время рестарта: 356 запросов `/top` и `/rank` за 25 с окна, все `200`. Первая запись сразу после рестарта — `503` (`the database system is starting up`), повтор через 0.5 с — `200`. Воркер записал в лог `postgres connection lost`, переподключился и снова взял leader lock; новая запись дошла до `top` |
| `api` | совпадают с исходными | stateless |
| `worker` | совпадают с исходными | leader lock взят заново, backlog 0 |
| новая запись после всех рестартов | `dave 100` встал после carol | доставка работает, tie-break сохранён |

Итог: потерь данных и изменений порядка нет, ни один процесс не перезапускался. `restart: unless-stopped` у API и воркера в compose оставлен как страховка от любых других падений процесса.

История: первая такая проверка нашла дефект — при рестарте PostgreSQL пул `pg` получал ошибку на простаивающем соединении без обработчика, и Node завершал API и воркер; чтения после истечения кеша сезона отвечали `500`. Исправлено: обработчики ошибок соединений у `pg.Pool` и `ioredis`, кеш сезона отдаёт последнее известное значение, воркер переподключается сам. Регрессионный тест — `test/pg-outage.test.ts`.

## Масштабирование

- **API** stateless, `k8s/api.yaml`: Deployment с 2 репликами и HPA по CPU (70%, от 2 до 10 подов). Потолок 10 задан соединениями PG: `10 × PG_POOL_SIZE 10 = 100` плюс воркеры и миграции укладываются в `max_connections = 200` с запасом, а при 20 подах пул API один занял бы весь лимит. Больше подов — только с PgBouncer. Для production добавить RPS на под и p95 через Prometheus Adapter.
- **Воркер** (`k8s/worker.yaml`): 2 реплики, активна одна (leader lock), HPA не применяется — водяной знак требует одного последовательного писателя. Метрики на `:9100/metrics`: `outbox_backlog`, `outbox_lag_seconds`, счётчики пачек, ошибок и rebuild. Рост нагрузки — шардирование по `hash(player_id)` с воркером и водяным знаком на шард.
- **Хранилища** HPA не масштабирует: чтения Redis — репликами, записи PG — вертикально.

Применить: `kubectl apply -k k8s/` (образ `leaderboard-service:dev`, строка подключения в Secret в `configmap.yaml`).

**Манифеста PostgreSQL в `k8s/` нет** — предполагается внешний managed PostgreSQL (RDS, Cloud SQL и т. п.) с бэкапами и репликой. Перед применением нужно указать его адрес и пароль в `DATABASE_URL` (Secret `leaderboard-secrets`) и убедиться, что `max_connections` не меньше 200 (см. расчёт выше). Redis в манифестах есть (`k8s/redis.yaml`), но одним экземпляром без реплики. `migrate-job.yaml` нужно дождаться до выкатки API: kustomize порядок запуска не гарантирует.

## Известные ограничения

- `POST /score` не идемпотентен: повтор запроса клиентом после таймаута удвоит очки. Решение — `Idempotency-Key`/`match_id` с уникальным индексом, в задание не входит.
- `|score| < 2 097 152` и не более 4.29 млрд обновлений за сезон (кодирование tie-break).
- Чтения — eventual consistency с лагом воркера; на границе сезона до 1 с (TTL кеша активного сезона) отдаётся старый сезон.
- При недоступном Redis чтения отвечают `503`; при недоступном PG — записи.
- Отрицательные `score_delta` и отрицательный итог допускаются (допущение по открытому вопросу RFC).
- Любая запись в `player_scores` в обход outbox (seed, ручные правки) обязана заканчиваться `rebuild --force` и `setval('tie_seq', …)`, иначе водяной знак не заметит потерю Redis, а guard отбросит обновления seeded-игроков. `npm run seed` делает это сам.
- Redis при остановке должен получать `SIGTERM` и достаточный grace period (30 с в compose, 60 с в k8s): `SIGKILL` теряет хвост AOF, что водяной знак поймает, но ценой rebuild.

## Результаты нагрузочных тестов

**Стенд.** Apple M2 Pro (12 ядер, 16 ГБ). PostgreSQL 17 и Redis 7.4 в Docker Desktop (VM: 12 CPU, 7.6 ГБ). API и воркер — нативные процессы Node 22. Генератор нагрузки `grafana/k6` 0.54 в Docker **на том же хосте**, прогоны по 30 с, `constant-arrival-rate`. Хост во время измерений был занят посторонними приложениями (load average 6–10 во время серии на 10 млн), поэтому хвосты задержек включают конкуренцию за CPU с генератором и не являются характеристикой сервиса. Сырые отчёты — в `k6/results/`.

**Seed, rebuild, память.**

| Игроков | `COPY` | Полный rebuild | Redis `used_memory` | Партиция PG |
|---|---|---|---|---|
| 100 тыс. | 0.18 с | 0.34 с | 10.6 МБ | — |
| 1 млн | 1.2 с | 2.9 с | 91 МБ | 107 МБ |
| 10 млн | 11.4 с | 43.8 с | 1012 МБ | 1067 МБ (heap 766 МБ) |

Redis: около 106 байт на игрока при `player_id` из 10 символов. Оценка RFC (120–150 байт при 32 символах) согласуется. На время rebuild (44 с на 10 млн) чтения отдают старый снимок, лаг растёт на это время.

**Задержки HTTP (мс), один инстанс API.**

| Игроков | Сценарий | RPS факт / цель | p50 | p95 | p99 | Ошибки |
|---|---|---|---|---|---|---|
| 100 тыс. | write | 1000 / 1000 | 0.88 | 4.2 | 34.5 | 0 |
| 100 тыс. | read | 9995 / 10 000 | 1.6 | 4.6 | 12.6 | 0 |
| 100 тыс. | mixed | 10 739 / 11 000 | 2.5 | 60 | 228 | 0 |
| 1 млн | write | 1000 / 1000 | 0.80 | 1.3 | 2.7 | 0 |
| 1 млн | read | 9969 / 10 000 | 1.6 | 5.3 | 21.5 | 0 |
| 1 млн | mixed | 10 999 / 11 000 | 1.9 | 8.4 | 24.3 | 0 |
| 1 млн | mixed, **2 инстанса API** | 10 984 / 11 000 | 1.7 | 4.9 | 14.3 | 0 |
| 10 млн | read | 9903 / 10 000 | 1.7 | 21.6 | 118 | 0 |
| 10 млн | mixed | 9779 / 11 000 | 2.5 | 155 | 505 | 0 |

Mixed на 1 млн по эндпоинтам: `POST /score` p95 12.7 / p99 52.7, `top` p95 7.9, `rank` p95 8.2. Второй инстанс API снимает хвост: сервис stateless, и это ровно то, что делает HPA.

**10 млн: что показали дополнительные замеры.** Первый прогон read дал p95 309 мс: он совпал по времени с autovacuum/analyze только что залитой партиции (видно в `pg_stat_user_tables`). Повторы на спокойной БД дали p95 84 мс, а с ограничением VU генератора (600 на сценарий) — 21.6 мс при тех же 9.9k RPS. При этом 300 последовательных запросов без нагрузки на 10 млн: `rank` медиана 0.90 / p95 2.0 мс, `top` 0.88 / 1.3 мс, то есть как на 1 млн. Redis по `INFO commandstats`: `ZREVRANK` 12.7 мкс, `ZRANGE` 8.1 мкс, скрипт rank 36.7 мкс на вызов. Вывод: путь данных на 10 млн не деградирует (O(log N) подтверждается), хвост под нагрузкой создаёт генератор в той же VM, у которого число VU растёт вслед за любым всплеском задержки. Mixed на 10 млн с одного инстанса целевые 11k RPS не набрал (k6 отбросил ~1200 итераций/с); для честной цифры нужен отдельный хост под генератор.

**Лаг outbox** (`outbox_lag_seconds`, выборка каждые 4 с во время mixed): 15–75 мс на 1 млн, 18–170 мс на 10 млн; backlog 13–280 событий при 1000 записей/с. Интервал опроса воркера 50 мс входит в лаг.
