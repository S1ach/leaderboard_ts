# Сервис сезонного лидерборда

Рейтинг игроков внутри сезона. После матча игроку начисляются очки, они накапливаются; клиент запрашивает топ сезона и позицию игрока с соседями. Сезон длится календарный месяц, затем рейтинг начинается заново, а история прошлых сезонов остаётся в PostgreSQL. При равных очках выше тот, кто набрал их раньше.

Закрываемые требования: накопительные начисления, топ-N и позиция с соседями, стабильный порядок при равенстве очков, данные переживают перезапуск любого компонента, ориентир по нагрузке — 1000 записей и 10 000 чтений в секунду при рейтинге до 10 млн игроков.

```
POST /score ──▶ PostgreSQL ──▶ outbox worker ──▶ Redis ZSET ◀── GET /leaderboard/top
             (UPSERT + outbox   (Lua apply,        leaderboard:{season}   GET /leaderboard/rank/{id}
              в одной tx)        водяной знак)
```

## Запуск

Нужен только Docker. Одна команда поднимает PostgreSQL 17, Redis 7 (AOF everysec, noeviction), миграции, API и воркер:

```bash
docker compose up --build
```

```bash
curl -s -X POST localhost:3000/score -H 'content-type: application/json' \
     -d '{"player_id":"alice","score_delta":100}'
# {"player_id":"alice","season_id":202609,"score":100}

curl -s 'localhost:3000/leaderboard/top?limit=10'
# {"season_id":202609,"entries":[{"rank":1,"player_id":"alice","score":100}]}

curl -s 'localhost:3000/leaderboard/rank/alice?n=5'
# {"season_id":202609,"player":{"rank":1,"player_id":"alice","score":100},"above":[],"below":[]}
```

Порты на хосте: API `3000`, метрики воркера `9100`, PostgreSQL `5433`, Redis `6380`. Если порт занят, достаточно переопределить переменную — её читают и compose, и приложение, и тесты:

```bash
POSTGRES_PORT=15433 docker compose up --build
```

Остальные переменные — в [.env.example](.env.example); compose читает `.env` сам.

| Команда | Что делает |
|---|---|
| `npm run migrate` | применяет `migrations/*.sql`, forward-only, под advisory lock |
| `npm run create-season -- 202610` | создаёт сезон и его партицию заранее |
| `npm run rebuild-leaderboard -- [--force]` | восстанавливает рейтинг в Redis из PostgreSQL |
| `npm run seed -- --players 1000000` | заливает игроков через `COPY` и пересобирает рейтинг |
| `PLAYERS=1000000 k6/run-all.sh` | нагрузочные сценарии write, read, mixed с сохранением отчётов |
| `npm run k6:write` / `k6:read` / `k6:mixed` | один сценарий без сохранения отчёта |

Подробности по этим командам — в [docs/operations.md](docs/operations.md). Полная схема API — в [docs/openapi.yaml](docs/openapi.yaml), служебные ручки: `GET /health` (liveness, хранилища не проверяет) и `GET /ready` (readiness, проверяет PostgreSQL и Redis).

**Тесты.** 45 тестов на vitest: unit на кодирование порядка и интеграционные против реальных PostgreSQL и Redis — начисления и конкурентность, порядок при равных очках, идемпотентность доставки, восстановление после потери данных в Redis, поведение при недоступном PostgreSQL.

```bash
docker compose up -d postgres redis
npm install
npm test                       # база leaderboard_test создаётся автоматически
```

План и результаты сквозного HTTP smoke-тестирования: [план](docs/smoke-test-plan.md), [отчёт и найденные дефекты](docs/smoke-test-report.md).

## Архитектура

PostgreSQL — source of truth, Redis Sorted Set — модель для чтения, между ними transactional outbox. Начисление очков и событие о нём пишутся одной транзакцией в PostgreSQL, поэтому подтверждённая запись не теряется и рассинхронизация между хранилищами невозможна. Отдельный воркер читает события пачками и применяет их в Redis, откуда обслуживаются оба чтения: топ за O(log N + M), позиция игрока за O(log N). Прямые чтения из PostgreSQL для позиции пришлось бы делать через подсчёт строк выше игрока — это O(позиции) и на 10 млн игроков не выдерживает тысяч запросов в секунду. Плата за такую схему — отставание чтений на время доставки и один дополнительный процесс.

### Альтернативы

N — число игроков сезона (до 10 млн), M — размер ответа. Значения — асимптотика и качественная оценка, не замеры.

| Критерий | A. Только PostgreSQL | B. Только Redis (AOF) | C. PG + Redis, dual write | **D. PG + outbox + Redis (выбран)** | E. PG + CDC (Debezium) + Redis |
|---|---|---|---|---|---|
| **Консистентность** | строгая: чтение видит свою запись | строгая | нет гарантии: сбой между коммитом в PG и `ZADD` оставляет Redis расходящимся навсегда | eventual: чтения отстают на лаг воркера, но всегда сходятся к PG | eventual, как D |
| **Надёжность записи** | подтверждённое не теряется | `appendfsync everysec`: при падении теряется до ~1 с подтверждённых записей; `always` — надёжно, но fsync на каждую запись | в PG не теряется, в Redis может потеряться | подтверждённое не теряется: счёт и событие в одной транзакции PG | как D |
| **Чтение top при 10 млн** | O(log N + M) по индексу `(season, score DESC, tie_seq)` — дёшево | O(log N + M), `ZRANGE … REV` | O(log N + M) | O(log N + M) | O(log N + M) |
| **Чтение rank при 10 млн** | `COUNT(*)` строк выше игрока — O(позиция): для середины рейтинга ~5 млн записей индекса на один запрос, при тысячах rank/с не выдерживает | O(log N), `ZREVRANK` | O(log N) | O(log N), позиция и соседи одним Lua-скриптом | O(log N) |
| **Запись** | один UPSERT, но индекс по `score` меняется при каждом начислении: нет HOT update, больше WAL и bloat | Lua read-modify-write, O(log N), в памяти | UPSERT + синхронный вызов Redis в запросе: задержка обоих хранилищ, при недоступном Redis — ошибка или пропуск | UPSERT + INSERT в outbox в одной транзакции; Redis в пути записи не участвует | один UPSERT, изменения читаются из WAL |
| **Восстановление** | не требуется, стандартные бэкапы и реплики PG | только из AOF/RDB; потерянное не восстановить, истории прошлых сезонов нет | ручная сверка; неизвестно, когда Redis разошёлся | автоматическое: водяной знак обнаруживает потерю в Redis, пересборка из PG за O(N) | пересборка из PG или перечитывание с позиции слота |
| **Сложность эксплуатации** | низкая: одно хранилище | низкая по числу компонентов, но весь рейтинг в памяти, настройки persistence критичны | низкая на старте, хрупкая в сбоях | средняя: воркер (один активный), очистка outbox и autovacuum, мониторинг backlog | высокая: Kafka Connect/Debezium, слоты репликации (при остановке потребителя копится WAL) |
| **Главный недостаток** | rank не масштабируется | нет source of truth | тихая порча рейтинга | лаг чтений и лишний процесс | лишняя инфраструктура для задания |

**Почему D.** Это самый простой вариант, который одновременно даёт O(log N) для позиции игрока, не теряет подтверждённые записи и сам сходится после частичных сбоев: всё, что попадает в Redis, сначала закоммичено в PostgreSQL, а потерю данных в Redis воркер обнаруживает и чинит пересборкой. CDC дал бы те же гарантии, но ценой Kafka Connect и слотов репликации. Подробный разбор — в [docs/design.md](docs/design.md), раздел 2.1.

## Ключевые решения

**Накопление очков.** `POST /score` выполняет один запрос: `INSERT … ON CONFLICT DO UPDATE SET score = score + delta` и вставку в outbox с итоговым счётом, а не дельтой. Конкурентные начисления сериализуются блокировкой строки, потерянных обновлений нет — 200 параллельных `+1` дают ровно 200. Итоговый счёт в событии делает повторное применение безопасным.

**Стабильный порядок при равных очках.** Sorted Set при равном score сортирует по имени игрока, поэтому порядок закодирован в сам score: `score * 2^32 + (2^32 - 1 - tie_local)`, где `tie_local` — номер обновления в сезоне из последовательности PostgreSQL. Всё помещается в 2^53, так что double точен, а среди равных очков выше оказывается тот, кто набрал их раньше. PostgreSQL и Redis упорядочивают по одному и тому же значению, поэтому пересборка даёт тот же порядок, что и штатная доставка.

**Перезапуск любого компонента.** PostgreSQL и Redis держат данные в volume, Redis пишет AOF с `appendfsync everysec`. При отказе PostgreSQL записи отвечают `503`, а чтения продолжают отдавать рейтинг из Redis; при отказе Redis наоборот — записи копятся в outbox и доезжают после восстановления. Процессы переживают обрыв соединений: воркер открывает новую сессию и заново берёт leader lock. Проверено вручную перезапуском каждого сервиса по очереди — процедура и результат в [docs/operations.md](docs/operations.md).

**Восстановление Redis.** Каждая пачка событий получает номер: максимальный применённый хранится в Redis, последний закоммиченный — в PostgreSQL. Если номер в Redis меньше, значит потерян хвост AOF, случился `FLUSHALL` или это отставшая реплика — воркер сам пересобирает сезон из PostgreSQL, читая партицию во временный ключ и подменяя рабочий одной атомарной операцией. Плановый рестарт с целым AOF пересборку не вызывает, а читатели во время неё видят прошлый снимок, а не половину нового.

## Смена сезона

Активный сезон определяется временем транзакции в PostgreSQL: у каждого сезона своя партиция `player_scores_<id>` и свой ключ Redis, поэтому на границе ничего запускать не нужно — записи уходят в новую партицию, воркер сам создаёт новый ключ.

1. Заранее создать следующий сезон: `npm run create-season -- 202610` (в production — плановая задача).
2. Если сезон не создан, после границы `POST /score` отвечает `503 no_active_season` и начисление не сохраняется.
3. После границы и доставки поздних событий — выгрузить итоги, `DETACH PARTITION … CONCURRENTLY`, архивировать таблицу, ключ Redis снять через `UNLINK`.

Команды и проверки — в [docs/operations.md](docs/operations.md#смена-сезона).

## Масштабирование и HPA

- **API** stateless: HPA по CPU с целью 70 %, от 2 до 10 реплик ([k8s/api.yaml](k8s/api.yaml)). Потолок 10 задан соединениями PostgreSQL, а не CPU: `10 × PG_POOL_SIZE 10 = 100` плюс воркеры и миграции укладываются в `max_connections = 200`, а 20 подов заняли бы весь лимит. Дальше — только через PgBouncer. В production к CPU стоит добавить RPS на под и p95 через Prometheus Adapter.
- **Воркер** под HPA не ставится: водяной знак корректен только при одном последовательном писателе, поэтому реплик две, а активна одна (leader lock в PostgreSQL, вторая — горячий резерв, [k8s/worker.yaml](k8s/worker.yaml)). При росте нагрузки воркер шардируется по `hash(player_id) % K`: у каждого шарда свой воркер, своя последовательность пачек и свой водяной знак.
- **Хранилища** HPA не масштабирует: чтения Redis — репликами, запись PostgreSQL — вертикально, затем шардированием.

Манифеста PostgreSQL нет — предполагается внешний managed-сервис. Подробнее — в [docs/operations.md](docs/operations.md#kubernetes-и-масштабирование).

## Нагрузочное тестирование

Сценарии k6: `write` (1000 записей/с), `read` (10 000 чтений/с поровну на top и rank) и `mixed` (1000 записей/с и 10 000 чтений/с одновременно). Залить игроков и прогнать все три:

```bash
npm run seed -- --players 1000000
PLAYERS=1000000 k6/run-all.sh
```

Скрипт сохраняет в `k6/results/` сводку k6, её вывод с параметрами прогона в заголовке и лаг доставки outbox. Переменные, методика и шаблон таблиц результатов — в [docs/benchmarks.md](docs/benchmarks.md).

## Известные ограничения

- `POST /score` не идемпотентен: повтор после таймаута начислит очки дважды. Решение — `Idempotency-Key` или `match_id` с уникальным индексом.
- `|score| < 2 097 152` и около 2.1 млрд начислений за сезон — следствие кодирования порядка при равных очках: номера версий берутся из последовательности, и обновление существующего игрока расходует два номера из 4.29 млрд.
- Чтения отстают на лаг доставки, а на границе сезона до секунды отдают прошлый сезон.
- При недоступном Redis чтения отвечают `503`, при недоступном PostgreSQL — записи.
- Отрицательные начисления и отрицательный итоговый счёт разрешены (допущение по открытому вопросу из [docs/design.md](docs/design.md), раздел 9).
- Сезоны создаются заранее вручную: если следующий сезон не создан, после границы начисления отклоняются с `503` и не сохраняются.
- Любая запись в `player_scores` мимо outbox обязана заканчиваться пересборкой с `--force` и продвижением `tie_seq`; `npm run seed` делает это сам.
- Redis при остановке должен получать `SIGTERM` и достаточный grace period (30 с в compose, 60 с в k8s): `SIGKILL` теряет хвост AOF, и водяной знак поймает это ценой пересборки.
- Метрики отдаёт только воркер (`:9100/metrics`); у API их нет, как и дашбордов и алертов.
