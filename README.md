# Сервис сезонного лидерборда

Рейтинг игроков внутри сезона: после матча игроку начисляются очки (накопительно), клиент запрашивает топ сезона и позицию игрока с соседями. Сезон длится календарный месяц, затем рейтинг начинается заново, история прошлых сезонов остаётся в PostgreSQL. При равных очках выше тот, кто набрал их раньше.

PostgreSQL — source of truth, доставка в Redis через transactional outbox, чтения — из Redis Sorted Set. Обоснование решений — в [docs/RFC-001-leaderboard.md](docs/RFC-001-leaderboard.md), схема API — в [docs/openapi.yaml](docs/openapi.yaml).

```
POST /score ──▶ PostgreSQL ──▶ outbox worker ──▶ Redis ZSET ◀── GET /leaderboard/top
             (UPSERT + outbox   (Lua apply,        leaderboard:{season}   GET /leaderboard/rank/{id}
              в одной tx)        водяной знак)
```

## Запуск

Нужен только Docker. Одна команда поднимает PostgreSQL 17, Redis 7 (AOF everysec, noeviction), миграции, API и воркер:

```bash
docker compose up --build
```

Порты на хосте: API `3000`, метрики воркера `9100`, PostgreSQL `5433`, Redis `6380`. Если порт занят, достаточно переопределить переменную — её читают и compose, и приложение, и тесты: `POSTGRES_PORT=15433 docker compose up --build`. Полный список переменных — в [.env.example](.env.example); значения можно положить в `.env`, compose читает его сам.

Проверка:

```bash
curl -s -X POST localhost:3000/score -H 'content-type: application/json' \
     -d '{"player_id":"alice","score_delta":100}'
# {"player_id":"alice","season_id":202609,"score":100}
curl -s 'localhost:3000/leaderboard/top?limit=10'
curl -s 'localhost:3000/leaderboard/rank/alice?n=5'
curl -s localhost:9100/metrics          # backlog и лаг outbox
```

Для разработки (нужен Node 22) хранилища удобнее держать в Docker, а API и воркер запускать нативно: `docker compose up -d postgres redis`, затем `npm install`, `npm run migrate`, `npm run dev:api` и `npm run dev:worker`.

| Команда | Что делает |
|---|---|
| `npm run migrate` | применяет `migrations/*.sql` (forward-only, под advisory lock) |
| `npm run create-season -- 202610` | создаёт сезон, его партицию и строку `worker_state` заранее |
| `npm run rebuild-leaderboard -- [--season 202609] [--force]` | восстанавливает Redis из PostgreSQL |
| `npm run seed -- --players 1000000` | заливает игроков через `COPY`, продвигает `tie_seq`, делает `rebuild --force` |
| `npm test` | интеграционные тесты; нужны поднятые `postgres` и `redis`, база `leaderboard_test` создаётся сама |
| `npm run k6:write` / `k6:read` / `k6:mixed` | нагрузочные сценарии |

## API

| Метод | Ответ |
|---|---|
| `POST /score` `{"player_id","score_delta"}` | `200 {"player_id","season_id","score"}` — новый абсолютный счёт. `400` валидация (пустой id, `score_delta = 0`, не целое), `422` счёт вне диапазона, `503` нет сезона или PostgreSQL недоступен |
| `GET /leaderboard/top?limit=100` | `{"season_id","entries":[{"rank","player_id","score"}]}`, `limit` 1…1000 |
| `GET /leaderboard/rank/{player_id}?n=5` | `{"season_id","player":{…},"above":[…],"below":[…]}`, `n` 0…50, `404` для игрока вне рейтинга |
| `GET /health` | liveness: `200 {"status":"ok"}`; хранилища не проверяет, чтобы их отказ не перезапускал API |
| `GET /ready` | readiness: `200`/`503` с состоянием PostgreSQL и Redis |

Сортировка: по убыванию очков, при равенстве выше тот, кто раньше получил этот счёт. Позиции с 1, без дублей. `POST /score` возвращает счёт сразу, `/top` и `/rank` отстают на лаг доставки — десятки миллисекунд, замеры ниже.

## Как это устроено

**Запись.** Один SQL-запрос в одной транзакции: `INSERT … ON CONFLICT DO UPDATE SET score = score + delta, tie_seq = nextval()` плюс вставка в `leaderboard_outbox` с абсолютным счётом, а не дельтой. Сезон выбирается по времени БД. Конкурентные начисления сериализуются блокировкой строки в `ON CONFLICT`, потерянных обновлений нет: 200 параллельных `+1` дают ровно 200.

**Tie-break.** Sorted Set при равных очках сортирует по имени, поэтому порядок закодирован в сам score: `score * 2^32 + (2^32 - 1 - tie_local)`, где `tie_local = tie_seq - season.tie_base`. Всё меньше 2^53, значит double точен. Отсюда ограничения: `|score| < 2^21` и до 2^32 обновлений за сезон.

**Воркер.** Активен один экземпляр (leader lock в PostgreSQL), второй ждёт. Цикл: выбрать пачку до 500 событий `FOR UPDATE SKIP LOCKED`, схлопнуть события одного игрока, применить одним Lua-вызовом на сезон, удалить строки, закоммитить. Lua применяет событие, только если его `tie_local` новее сохранённого, поэтому повторы и перестановки безопасны.

**Водяной знак.** Каждая пачка получает номер из последовательности: Redis хранит максимальный применённый в `leaderboard:{season}:meta`, PostgreSQL — последний закоммиченный в `worker_state`. Если номер в Redis меньше, значит потерян хвост AOF или это отставшая реплика — воркер запускает пересборку. Плановый рестарт с целым AOF пересборку не вызывает, `FLUSHALL` ловится по отсутствию `meta`.

**Пересборка.** Под эксклюзивным advisory lock (воркер держит shared на каждую пачку, поэтому гонки нет) читает партицию keyset-пагинацией во временный ключ и меняет его на рабочий одним Lua-скриптом `RENAME` + `HSET meta`. Читатели видят старый ключ, а не половину нового.

Доказательство корректности водяного знака и полный разбор отказов — в RFC, разделы 3.3 и 4.4.

## Смена сезона

Сезон — это строка в `seasons` с границами `[starts_at, ends_at)`, партиция `player_scores_<id>`, строка `worker_state` и ключи Redis. Какой сезон активен, определяет время транзакции в PostgreSQL; отдельного кода переключения нет. Автоматического планировщика тоже нет: шаги ниже выполняются вручную, в production их берёт на себя плановая задача (Kubernetes CronJob или pg_partman).

**Заранее создать следующий сезон** — за несколько дней до конца текущего:

```bash
npm run create-season -- 202610        # границы по умолчанию: календарный месяц UTC
```

`create_season()` одной транзакцией вставляет сезон с `tie_base = nextval('tie_seq')`, создаёт партицию и строку `worker_state`. Сезоны не могут пересекаться, повторный вызов для того же id — ошибка. Первый сезон создаёт миграция `002_initial_season.sql`.

**На границе** запускать нечего: записи уходят в новую партицию, воркер доставляет их в новый ключ и сам создаёт `meta` первой пачкой, события старого сезона из outbox доезжают в старый ключ. Чтения до секунды (TTL кеша сезона) показывают прошлый сезон; новый рейтинг стартует пустым. Лимит 2^32 обновлений считается для каждого сезона отдельно.

**Если следующий сезон не создан**, активного сезона после `ends_at` нет: `POST /score` отвечает `503 no_active_season` и начисление **не сохраняется**, чтения тоже отвечают `503`. Лечится созданием сезона, перезапуск сервисов не нужен, поэтому в production нужен алерт «на следующий месяц сезона нет».

**Архивирование** — после того как поздние события доставлены (`SELECT count(*) FROM leaderboard_outbox WHERE season_id = 202609` вернул 0). Команды проверены на PostgreSQL 17:

```sql
-- итоги в порядке рейтинга: те же очки и tie_seq, что и в Redis
\copy (SELECT row_number() OVER (ORDER BY score DESC, tie_seq) AS rank, player_id, score FROM player_scores_202609 ORDER BY score DESC, tie_seq) TO 'season_202609.csv' WITH CSV HEADER
-- CONCURRENTLY не блокирует запись в текущий сезон
ALTER TABLE player_scores DETACH PARTITION player_scores_202609 CONCURRENTLY;
```

Дальше отсоединённая таблица уходит в холодное хранилище (`pg_dump -t player_scores_202609`) и удаляется, а ключи Redis после периода хранения снимаются через `UNLINK 'leaderboard:{202609}' 'leaderboard:{202609}:meta'` — он освобождает память в фоне и не блокирует Redis, в отличие от `DEL` на ключе с миллионами элементов. Строки `seasons` и `worker_state` можно оставить: это история границ, а проверка водяного знака смотрит только сезоны с `ends_at > now()`.

Важно: после `DETACH` не запускать `rebuild-leaderboard` для этого сезона — партиция больше не видна через `player_scores`, пересборка получит 0 строк и заменит ключ пустым.

## Почему такая архитектура

N — число игроков сезона (до 10 млн), M — размер ответа. Где не сказано иное, это асимптотика и качественная оценка: замерялся только выбранный вариант.

| Критерий | A. Только PostgreSQL | B. Только Redis | C. PG + Redis, dual write | **D. PG + outbox + Redis** | E. PG + CDC + Redis |
|---|---|---|---|---|---|
| Консистентность | строгая | строгая | может разойтись навсегда | eventual, сходится к PG | eventual, как D |
| Надёжность записи | не теряется | при падении теряется до ~1 с (AOF everysec) | в Redis может потеряться | не теряется: счёт и событие в одной транзакции | как D |
| Чтение top при 10 млн | O(log N + M) по индексу | O(log N + M) | O(log N + M) | O(log N + M) | O(log N + M) |
| Чтение rank при 10 млн | O(позиция): для середины рейтинга ~5 млн записей индекса на запрос | O(log N) | O(log N) | O(log N), позиция и соседи одним скриптом | O(log N) |
| Запись | UPSERT, но индекс по `score` растёт в WAL и мешает HOT update | Lua read-modify-write в памяти | UPSERT + синхронный Redis в запросе | UPSERT + INSERT в outbox, Redis вне пути записи | UPSERT, изменения идут из WAL |
| Восстановление | не требуется | только AOF/RDB, истории сезонов нет | ручная сверка | автоматическое: водяной знак и пересборка из PG за O(N) | пересборка или перечитывание с позиции слота |
| Эксплуатация | простая | простая, но весь рейтинг в памяти | хрупкая в сбоях | средняя: воркер, очистка outbox, мониторинг backlog | сложная: Debezium, слоты репликации |
| Главный минус | rank не масштабируется | нет source of truth | тихая порча рейтинга | лаг чтений и лишний процесс | лишняя инфраструктура |

**Выбран D:** это самый простой вариант, который одновременно даёт O(log N) для rank, не теряет подтверждённые записи и сам сходится после частичных сбоев. Цена — отставание чтений на время доставки и один дополнительный процесс.

## Тесты

`npm test` — 41 тест на vitest против реальных PostgreSQL и Redis:

- начисления: конкурентное накопление, валидация, `422` при переполнении, `503` без сезона, аудит-лог;
- порядок: раньше набравший выше, изменивший счёт опускается среди равных, пересборка даёт тот же порядок;
- доставка: идемпотентность, старое событие не перезаписывает новое, недоступный Redis, падение между применением и коммитом;
- восстановление: `STALE` и `NOMETA`, пропуск пересборки при целом водяном знаке, запись в обход outbox, блокировка воркера на время пересборки;
- API: top, rank с обрезкой у краёв, `404`, лаг между записью и чтением, поведение проб;
- недоступный PostgreSQL (TCP-прокси рвёт соединения): чтения отвечают из Redis, запись — `503`, после восстановления снова `200` без перезапуска процесса.

## Надёжность при перезапусках

Проверка вручную, 17.09.2026, на чистом стеке под отдельным именем проекта (`docker compose -p lb-clean up -d --build`), чтобы не задеть рабочие данные. Сценарий: шесть начислений, снимок `top` и `rank`, затем по очереди `docker compose -p lb-clean restart <сервис>` с ожиданием `/ready` и пустого backlog, снимок и сравнение с исходным.

Исходный рейтинг: `alice 120, bob 100, carol 100, dave 70` — bob выше carol, потому что набрал 100 раньше.

| Перезапуск | Результат | Детали |
|---|---|---|
| `redis` | рейтинг не изменился | AOF цел, водяной знак сошёлся, пересборки не было |
| `postgres` | рейтинг не изменился | процессы не падали (`RestartCount=0`); за 25-секундное окно 356 чтений, все `200`; первая запись после рестарта — `503` («database system is starting up»), повтор через полсекунды — `200`; воркер переподключился и снова взял leader lock |
| `api` | рейтинг не изменился | stateless |
| `worker` | рейтинг не изменился | leader lock взят заново, backlog 0 |
| запись после всех рестартов | `dave 100` встал после carol | доставка работает, порядок при равенстве сохранён |

**Почему в коде есть обработчики обрыва соединений.** Без них рестарт PostgreSQL завершал и API, и воркер: пул `pg` получает ошибку на простаивающем соединении, а необработанное событие `error` убивает процесс Node; чтения после истечения кеша сезона отвечали `500`. Сейчас такие ошибки логируются, кеш сезона отдаёт последнее известное значение, воркер открывает новую сессию и заново берёт leader lock. Покрыто тестом `test/pg-outage.test.ts`. `restart: unless-stopped` в compose остаётся страховкой от прочих падений.

## Масштабирование и Kubernetes

- **API** stateless: Deployment с 2 репликами и HPA по CPU 70 %, от 2 до 10 подов ([k8s/api.yaml](k8s/api.yaml)). Потолок задан не процессором, а соединениями: `10 подов × PG_POOL_SIZE 10 = 100` плюс воркеры и миграции укладываются в `max_connections = 200`, а 20 подов заняли бы весь лимит. Дальше — только с PgBouncer. В production к CPU стоит добавить RPS на под и p95 через Prometheus Adapter.
- **Воркер** ([k8s/worker.yaml](k8s/worker.yaml)): 2 реплики, активна одна. HPA неприменим — водяной знак требует одного последовательного писателя; масштабирование при росте нагрузки это шардирование по `hash(player_id)` со своим воркером и водяным знаком на шард. Метрики на `:9100/metrics`: `outbox_backlog`, `outbox_lag_seconds`, счётчики пачек, ошибок и пересборок.
- **Хранилища** HPA не масштабирует: чтения Redis — репликами, запись PostgreSQL — вертикально.

Применяется через `kubectl apply -k k8s/`. **Манифеста PostgreSQL нет** — предполагается внешний managed-сервис с бэкапами и репликой, его адрес и пароль задаются в Secret `leaderboard-secrets`. Redis в манифестах есть, но одним экземпляром без реплики, а `migrate-job.yaml` нужно дождаться до выкатки API: порядок kustomize не гарантирует.

## Известные ограничения

- `POST /score` не идемпотентен: повтор после таймаута начислит очки дважды. Решение — `Idempotency-Key` или `match_id` с уникальным индексом.
- `|score| < 2 097 152` и не более 4.29 млрд обновлений за сезон — следствие кодирования tie-break.
- Чтения отстают на лаг доставки, а на границе сезона до секунды отдают прошлый сезон.
- При недоступном Redis чтения отвечают `503`, при недоступном PostgreSQL — записи.
- Отрицательные начисления и отрицательный итоговый счёт разрешены (допущение по открытому вопросу RFC).
- Любая запись в `player_scores` в обход outbox обязана заканчиваться `rebuild --force` и `setval('tie_seq', …)`, иначе водяной знак не заметит потерю Redis, а guard отбросит обновления таких игроков. `npm run seed` делает это сам.
- Redis при остановке должен получать `SIGTERM` и достаточный grace period (30 с в compose, 60 с в k8s): `SIGKILL` теряет хвост AOF, и водяной знак поймает это ценой пересборки.

## Нагрузочные тесты

Все отчёты в [k6/results/](k6/results/) сняты 16.09.2026 с 19:10 до 19:24 на одной машине, поэтому строки таблиц сопоставимы между собой. Цифры взяты из JSON-сводок k6; то, для чего сырых файлов нет, помечено отдельно.

**Стенд.** Apple M2 Pro (12 ядер: 8 производительных и 4 энергоэффективных), 16 ГБ, macOS 26.6.2. Docker Desktop, Engine 27.4.0, VM `NCPU=12`, `MemTotal` 7.65 ГиБ. Node v22.12.0. PostgreSQL и Redis в контейнерах, API и воркер — нативные процессы, генератор `grafana/k6:0.54.0` в Docker **на том же хосте**. Версии и ресурсы VM сняты 17.09, на момент прогонов могли отличаться. Во время серии на 10 млн хост был занят посторонними приложениями (load average 6–10) — оценка по ходу прогонов, **сырые данные не сохранены**.

**Как повторить.** Данные заливаются `npm run seed -- --players N`, затем:

```bash
docker run --rm -i --add-host=host.docker.internal:host-gateway -v ./k6:/scripts \
  -e BASE_URL=http://host.docker.internal:3000 -e PLAYERS=1000000 -e DURATION=30s -e MAX_VUS=2000 \
  grafana/k6:0.54.0 run --summary-export=/scripts/results/mixed-1m.json /scripts/mixed.js \
  | tee k6/results/mixed-1m.txt
k6/sample-lag.sh > k6/results/mixed-1m-lag.txt   # параллельно, в другом терминале
```

Переменные сценариев: `BASE_URL` (несколько адресов через запятую — так снят прогон с двумя инстансами), `PLAYERS` (диапазон id, должен быть не больше числа игроков в seed), `DURATION`, `RATE` для `write.js` и `read.js`, `WRITE_RATE` для `mixed.js` (чтения идут по `5 × WRITE_RATE` на top и rank), `MAX_VUS`. Скрипты `npm run k6:*` передают только `BASE_URL`, поэтому `PLAYERS` в них остаётся равным 100 000. Скрипт `k6/sample-lag.sh` **восстановлен по формату записанных файлов, исходный не сохранился**.

Важная особенность метода: при `constant-arrival-rate` k6 запускает итерации с заданной частотой, и если свободных виртуальных пользователей нет, итерация **отбрасывается** (`dropped_iterations`) и в задержки не попадает. Поэтому заметный dropped означает, что целевая нагрузка не достигнута, а p95 и p99 занижены — самые медленные моменты частично не измерены.
