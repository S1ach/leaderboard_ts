## 1. Продуктовый контекст

**Что делаем.** Сервис сезонного рейтинга игроков. После матча игрок получает очки, они прибавляются к его счёту. Игроки видят топ рейтинга и своё место среди соседей. Сезон длится месяц, затем рейтинг начинается заново.

**Фичи:**

1. Начисление очков после матча (накопительно).
2. Топ-N игроков сезона.
3. Позиция игрока и N соседей сверху и снизу.
4. Смена сезона без потери истории прошлых сезонов.

**Правило рейтинга.** Больше очков — выше. При равенстве выше тот, кто **раньше** получил этот счёт.

**Что хотим получить в конце:**

- сервис, который поднимается через `docker compose up`;
- данные переживают перезапуск любого компонента;
- нагрузочные тесты с реальными измерениями;
- манифесты Kubernetes с HPA;
- README с обоснованием решений и честными ограничениями.

**Цели по качеству** (ориентиры для нагрузочных тестов, не измеренные значения): 1000 записей/с, ~10 000 чтений/с, до 10 млн игроков, p95 чтения — десятки миллисекунд.

**Не делаем:** авторизацию, frontend, автоматическую смену сезона в коде (только описание), брокеры сообщений.

## 2. Техническое описание

### 2.1. Рассмотренные варианты

| Критерий | A. Только PG | B. Только Redis | C. PG + Redis, dual write | **D. PG + outbox + Redis** |
|---|---|---|---|---|
| Consistency | строгая | строгая | возможна вечная рассинхронизация | eventual, лаг — миллисекунды, сходится гарантированно |
| Надёжность | высокая | потеря до ~1 с при падении (AOF everysec) | потеря в Redis при частичном сбое | подтверждённое не теряется |
| Чтение top | дёшево (индекс) | O(log N + M) | O(log N + M) | O(log N + M) |
| Чтение rank | `COUNT(*)` выше игрока — O(позиция), дорого | O(log N) | O(log N) | O(log N) |
| Запись | 1 UPSERT | 1 ZADD | UPSERT + ZADD в запросе | UPSERT + INSERT в одной транзакции |
| Восстановление | не нужно | только из AOF/RDB | ручная сверка | пересборка из PG |
| Компоненты | API, PG | API, Redis | API, PG, Redis | API, воркер, PG, Redis |
| Сложность | низкая | низкая | низкая, но хрупкая | средняя |

Ещё один вариант — CDC (logical replication / Debezium) вместо outbox-таблицы. Надёжно, но добавляет компоненты, которые не окупаются на этом масштабе.

**Выбран D.** Это самый простой вариант, который одновременно даёт O(log N) для rank, не теряет подтверждённые записи и сам сходится после частичных сбоев. Цена — отставание чтений на миллисекунды и один дополнительный процесс.

### 2.2. Реализация фич (верхнеуровнево)

```
POST /score ──▶ PostgreSQL: UPSERT счёта + событие в outbox (одна транзакция)
                     │
                     ▼
               outbox worker ──▶ Redis Sorted Set leaderboard:{сезон}
                                        ▲
GET /leaderboard/top, /rank ────────────┘
```

**Начисление очков.** Один SQL-запрос: UPSERT в `player_scores` с прибавлением дельты и вставка события в outbox. Событие содержит **итоговый** счёт, а не дельту, поэтому его повторное применение безопасно. Ответ содержит новый счёт из PG.

**Стабильный порядок при равных очках.** При каждом изменении очков игрок получает новый `tie_seq` из последовательности PG. В Redis очки и `tie_seq` упаковываются в один score:

```
tie_local   = tie_seq - season.tie_base          (0 … 2^32-1)
redis_score = score * 2^32 + (2^32 - 1 - tie_local)
```

При равных очках выше меньший `tie_local`, то есть кто раньше получил счёт. Ограничения: `|score| < 2^21 ≈ 2.09 млн` (иначе double теряет точность) и `tie_local < 2^32` за сезон (при 1000 записей/с за 31 день набегает ~2.7 млрд — запас есть). PG и Redis сортируют по одному и тому же `tie_seq`, поэтому пересборка даёт тот же порядок.

**Доставка в Redis.** Воркер читает события пачками, схлопывает несколько событий одного игрока в последнее и применяет Lua-скриптом, который пишет значение, только если его `tie_seq` новее сохранённого. Это защищает от повторов и от нарушения порядка.

**Топ.** `ZRANGE key 0 limit-1 REV WITHSCORES`, O(log N + M).

**Позиция и соседи.** Lua-скрипт: `ZREVRANK`, затем `ZRANGE … REV` вокруг позиции. Скрипт выполняется атомарно, поэтому позиция и соседи берутся из одного состояния. O(log N + M). Если игрока нет — `404`.

**Сезоны.** Таблица `seasons` задаёт границы, сезон записи определяется временем транзакции в БД. У каждого сезона своя партиция в PG и свой ключ в Redis. Смена сезона — это просто начало записи в новую партицию и новый ключ, без `DELETE`. Старый сезон: итоги архивируются, ключ Redis удаляется через `UNLINK`, партиция отключается (`DETACH`) и удаляется или архивируется. Партиции и строки `seasons` создаются заранее плановой задачей (cron / pg_partman) — в рамках задания вручную миграцией.

## 3. Инфраструктура

### 3.1. Компоненты

| Компонент | Технология | В docker-compose |
|---|---|---|
| API | Node.js, TypeScript, Fastify | да |
| Outbox worker | тот же образ, другая команда запуска | да |
| Реляционное хранилище | PostgreSQL 17 | да |
| Read model | Redis 7 (или Valkey) | да |
| Миграции | SQL-файлы, отдельный one-shot сервис | да |
| Метрики | текстовый `/metrics` воркера (раздел 3.4) | да, порт 9100 |
| Дашборды и алерты | Prometheus + Grafana | описание, не реализовано |
| Логи | stdout → Loki или ELK | описание |

**Reverse proxy не нужен.** В compose API слушает порт напрямую, в Kubernetes балансировку делает Service/Ingress.

### 3.2. Горизонтальное масштабирование

- **API stateless**, запускается N реплик. HPA по CPU (target 70%, min 2, max 10). Для production — ещё RPS на под и p95 latency через Prometheus Adapter.
- **Воркер** — один активный экземпляр и один резервный (leader lock через `pg_try_advisory_lock`). Единственность активного воркера — условие корректности водяного знака (4.4), поэтому HPA к нему не применяется. 1000 событий/с пачками по 500 — это единицы вызовов Redis в секунду, одного воркера хватает с запасом; при росте нагрузки — шардирование по `hash(player_id)`.
- **Соединения к PG:** `реплики API × размер пула ≤ max_connections`; при росте числа подов — PgBouncer.
- **HPA не масштабирует хранилища** — см. раздел 4.6.

### 3.3. Отказы

| Сценарий | Поведение | Потеря данных |
|---|---|---|
| Падает PG | `POST /score` → `503`. Чтения из Redis работают. | Нет: клиент повторит запрос. |
| Падает Redis | Чтения → `503`. Записи в PG продолжаются, события копятся в outbox. | Нет: воркер догонит после восстановления. |
| Рестарт API | Stateless, запросы уходят на другие поды. | Нет. |
| Падение воркера | События копятся в outbox, растёт лаг чтений; резервный экземпляр берёт lock лидера. | Нет. |
| Запись прошла только в PG | Событие лежит в outbox и будет доставлено. | Нет. |
| Запись прошла только в Redis | Невозможно: в Redis попадает только закоммиченное в PG. | — |
| Плановый рестарт Redis, AOF цел | Водяной знак сходится (`meta.batch >= worker_state.last_batch`), пересборка не нужна; недоставленное доедет из outbox. | Нет. |
| Рестарт Redis с потерей хвоста AOF | Скрипт apply или периодическая проверка возвращает `STALE` → пересборка. | Нет после пересборки. |
| Failover на отстающую реплику Redis | То же самое: `STALE` → пересборка. | Нет после пересборки. |
| `FLUSHALL`, потеря ключа | Нет `meta` при `last_batch > 0` → `NOMETA` → пересборка. | Нет после пересборки. |

**Настройки Redis:** `appendonly yes`, `appendfsync everysec`, `maxmemory` с запасом, `maxmemory-policy noeviction` — молчаливое вытеснение элементов рейтинга хуже, чем явная ошибка записи. В docker-compose и k8s Redis нужен достаточный grace period при остановке: `SIGTERM` делает fsync AOF, а `SIGKILL` по таймауту это обходит, и плановый рестарт превращается в потерю хвоста (водяной знак её поймает, но ценой пересборки).

Механизм обнаружения потери — водяной знак, раздел 4.4.

### 3.4. Мониторинг

Реализовано:

- **Воркер** отдаёт `GET /metrics` на отдельном порту (`WORKER_METRICS_PORT`, по умолчанию 9100) в текстовом формате Prometheus. Формат собирается вручную, без `prom-client`: зависимостей у сервиса и так немного, а метрик меньше десятка.
  - `outbox_backlog` и `outbox_lag_seconds` — размер очереди и возраст самого старого события, главная метрика здоровья доставки;
  - `worker_is_leader`, `worker_batches_total`, `worker_events_total`, `worker_applied_total`, `worker_errors_total`, `worker_rebuilds_total`.
- **API** отдаёт `GET /health`: `200`, если PG и Redis отвечают, иначе `503`; в теле — состояние каждого хранилища. В Kubernetes она используется и как liveness-, и как readiness-проба (`k8s/api.yaml`).

Не реализовано, описано как production-решение (приложение): отдельная readiness-проба `GET /ready`, метрики самого API через `prom-client` (RPS, ошибки и latency p50/p95/p99 по каждой ручке, размер пула соединений PG), `postgres_exporter` и `redis_exporter` (CPU, память, соединения, репликация, autovacuum), дашборды Grafana и алерты на backlog outbox, память Redis и долю ошибок 5xx.

### 3.5. Логи

Структурированные JSON-логи через встроенный в Fastify `pino` в stdout, с `request_id`. Сбор — агентом кластера (Promtail/Fluent Bit) в Loki или Elasticsearch, просмотр — в Grafana/Kibana. Подробнее — раздел 7.

### 3.6. CI/CD и выкатка

- **CI (GitHub Actions):** lint, typecheck, unit и интеграционные тесты с PG и Redis в service containers, сборка Docker-образа.
- **CD (описание):** образ с тегом коммита пушится в registry; миграции выполняются Kubernetes Job до выкатки; Deployment обновляется rolling update (вручную `kubectl apply` или через Argo CD). Readiness-проба не пускает трафик на под до готовности.
- **Миграции** только обратно совместимые (expand → deploy → contract), чтобы старая и новая версии API могли работать одновременно во время rolling update.

## 4. Хранилища данных

### 4.1. Выбор

- **PostgreSQL** — source of truth: транзакции, надёжность, партиционирование по сезонам, история.
- **Redis Sorted Set** — read model: top и rank за O(log N) без сортировки миллионов строк на каждый запрос.

### 4.2. Схема

Источник — `migrations/001_init.sql`; ниже он же, сокращённый до существенного.

```sql
CREATE TABLE seasons (
  id         integer PRIMARY KEY,          -- 202609
  starts_at  timestamptz NOT NULL,
  ends_at    timestamptz NOT NULL,
  tie_base   bigint NOT NULL,              -- значение tie_seq на старте сезона
  CHECK (starts_at < ends_at),
  EXCLUDE USING gist (tstzrange(starts_at, ends_at) WITH &&)
);

CREATE SEQUENCE tie_seq AS bigint CACHE 1;

CREATE TABLE player_scores (
  season_id  integer NOT NULL,
  player_id  text    NOT NULL,
  score      bigint  NOT NULL,
  tie_seq    bigint  NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (season_id, player_id),
  CHECK (abs(score) < 2097152)             -- предел кодирования, раздел 2.2
) PARTITION BY LIST (season_id);
-- Партиция сезона (player_scores_202609, fillfactor = 85) создаётся create_season().

CREATE TABLE leaderboard_outbox (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  season_id  integer NOT NULL,
  player_id  text    NOT NULL,
  score      bigint  NOT NULL,             -- итоговое состояние, не дельта
  tie_seq    bigint  NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- Обработанные строки удаляются, поэтому мёртвых строк много: агрессивный autovacuum.
ALTER TABLE leaderboard_outbox SET (
  autovacuum_vacuum_scale_factor = 0,
  autovacuum_vacuum_threshold = 5000,
  autovacuum_vacuum_cost_delay = 0,
  autovacuum_analyze_scale_factor = 0,
  autovacuum_analyze_threshold = 50000
);

-- Номер попытки обработки пачки — водяной знак (раздел 4.4).
CREATE SEQUENCE outbox_batch_seq AS bigint;

CREATE TABLE worker_state (
  season_id  integer PRIMARY KEY,
  last_batch bigint NOT NULL DEFAULT 0     -- последняя закоммиченная пачка сезона
);

-- create_season(id, starts_at, ends_at): строка сезона с tie_base = nextval('tie_seq'),
-- партиция player_scores_<id> и строка worker_state. Используется миграцией,
-- командой `npm run create-season` и тестами.
```

Решения:

- **Партиционирование `player_scores` по сезону.** Смена сезона не требует `DELETE` миллионов строк: старая партиция отключается (`DETACH`) и архивируется или удаляется. Ключ партиционирования входит в PK, как того требует PostgreSQL.
- **`season_id` — integer** (`202609`), а не строка: компактнее в строке и в индексе.
- **Сезоны не пересекаются** (`EXCLUDE`): иначе CTE выбора активного сезона вернул бы две строки и UPSERT выполнился бы дважды.
- **`tie_seq` с `CACHE 1`:** при большем кэше каждое соединение резервирует свой диапазон, и порядок между сессиями перестаёт соответствовать времени.
- **Отдельной колонки `version` нет** — её роль выполняет `tie_seq`, он растёт при каждом изменении очков игрока.
- **В outbox нет `processed_at`:** обработанные строки удаляются в той же транзакции, в которой поднимается водяной знак. Очередь остаётся короткой, а «обработано ли событие» — это факт его отсутствия, а не значение колонки.
- **`worker_state`** хранит водяной знак для обнаружения потери данных в Redis (раздел 4.4), `outbox_batch_seq` выдаёт его номера.

### 4.3. Индексы и почему именно такие

| Индекс | Зачем |
|---|---|
| PK `player_scores (season_id, player_id)` | UPSERT и поиск счёта игрока; keyset-чтение партиции при пересборке. |
| PK `leaderboard_outbox (id)` | Воркер берёт пачку `ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED`. |
| PK `worker_state (season_id)` | Чтение и `SELECT … FOR UPDATE` водяного знака по сезону. |
| **Нет** индекса `(season_id, score, tie_seq)` | Чтения идут из Redis, пересборка читает партицию целиком. Такой индекс удорожал бы каждую запись: изменение индексированной колонки запрещает HOT update, растут WAL и bloat. `fillfactor = 85` оставляет место на странице для HOT update. |
| **Нет** частичных индексов по `processed_at` | Колонки нет: события удаляются после обработки. В стационарном режиме в очереди лежат сотни строк, и сканирование по PK дешевле, чем поддержка отдельного индекса на каждой записи. |

**Подсчёты.** Динамических `COUNT(*)` нет ни в одной ручке. Позиция игрока — `ZREVRANK` (O(log N)), общее число игроков сезона — `ZCARD` (O(1), Redis хранит счётчик сам).

**Ограничения схемы:** сезоны не пересекаются (`EXCLUDE`), `tie_seq` с `CACHE 1`, счёт ограничен `CHECK (abs(score) < 2097152)`.

### 4.4. Взаимодействие с хранилищами по фичам

**POST /score — одна транзакция PG**

Здесь несколько действий, одно из них мутирующее, и они должны быть согласованы — поэтому транзакция обязательна. Всё делается одним запросом:

```sql
WITH s AS (
  SELECT id FROM seasons WHERE starts_at <= now() AND now() < ends_at
),
upsert AS (
  INSERT INTO player_scores (season_id, player_id, score, tie_seq)
  SELECT s.id, $1, $2, nextval('tie_seq') FROM s
  ON CONFLICT (season_id, player_id) DO UPDATE
    SET score = player_scores.score + EXCLUDED.score,
        tie_seq = EXCLUDED.tie_seq,
        updated_at = now()
  RETURNING season_id, player_id, score, tie_seq
)
INSERT INTO leaderboard_outbox (season_id, player_id, score, tie_seq)
SELECT season_id, player_id, score, tie_seq FROM upsert
RETURNING season_id, score;
```

| Риск | Как учтён |
|---|---|
| Гонка двух начислений одному игроку | `ON CONFLICT DO UPDATE` блокирует строку; вторая транзакция ждёт и прибавляет к обновлённому значению. Lost update невозможен. Проверяется тестом. |
| Рассинхрон PG и Redis | В Redis попадает только то, что закоммичено в PG, через outbox. |
| Падение посреди запроса | Транзакция откатывается целиком: нет ни счёта, ни события. |
| Счёт вышел за пределы | `CHECK` → откат, ответ `422`. |
| Нет активного сезона | Пустой результат → `503`. |
| Повтор запроса клиентом после таймаута | **Не учтён:** очки начислятся дважды. Известное ограничение (раздел 8). |

**Воркер — транзакция на пачку**

Работает **один активный воркер**, резервный ждёт на `pg_try_advisory_lock` лидера (почему один — ниже, в «Водяном знаке»). Lock лидера, shared-lock пересборки и транзакция пачки живут на одном выделенном соединении: обрыв соединения теряет и lock, и незакоммиченную пачку, процесс завершается, оркестратор его перезапускает. Иначе старый лидер мог бы коммитить пачки одновременно с новым.

Цикл (`src/lib/outbox.ts`):

1. `BEGIN`; `pg_try_advisory_xact_lock_shared(REBUILD_LOCK)`. Если занят — идёт пересборка: `ROLLBACK`, пауза, повтор.
2. `SELECT … FROM leaderboard_outbox ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED`.
3. Схлопнуть события одного игрока, оставив максимальный `tie_seq`.
4. `batch_id = nextval('outbox_batch_seq')`; для сезонов пачки `INSERT INTO worker_state … ON CONFLICT DO NOTHING`, затем `SELECT … FOR UPDATE` — это `expected`, последняя закоммиченная пачка сезона.
5. По одному вызову Lua-скрипта apply на сезон: он проверяет водяной знак и применяет события.
6. `DELETE` обработанных строк, `UPDATE worker_state SET last_batch = batch_id`, `COMMIT`.

```lua
-- KEYS[1] = leaderboard:{S}, KEYS[2] = leaderboard:{S}:meta
-- ARGV[1] = expected (worker_state.last_batch), ARGV[2] = batch_id,
-- далее тройки: member, redis_score, tie_local
local last = redis.call('HGET', KEYS[2], 'batch')
if not last then
  if tonumber(ARGV[1]) ~= 0 then
    return redis.error_reply('NOMETA')    -- ключ сезона потерян
  end
  last = '0'                              -- новый сезон: терять нечего
end
if tonumber(last) < tonumber(ARGV[1]) then
  return redis.error_reply('STALE')       -- Redis отстал от PG: потерян хвост AOF
end
local applied = 0
for i = 3, #ARGV, 3 do
  local cur = redis.call('ZSCORE', KEYS[1], ARGV[i])
  local newer = true
  if cur then
    local cur_tie = 4294967295 - (tonumber(cur) % 4294967296)
    newer = cur_tie < tonumber(ARGV[i + 2])   -- иначе старое событие или повтор
  end
  if newer then
    redis.call('ZADD', KEYS[1], ARGV[i + 1], ARGV[i])
    applied = applied + 1
  end
end
if tonumber(ARGV[2]) > tonumber(last) then
  redis.call('HSET', KEYS[2], 'batch', ARGV[2])
end
return applied
```

Проверка водяного знака встроена в сам скрипт, а не сделана отдельным `EXISTS` перед пачкой: иначе между проверкой и записью оставалось бы окно.

| Риск | Как учтён |
|---|---|
| Redis недоступен | Откат транзакции, события остаются в outbox, повтор с экспоненциальной задержкой. |
| Воркер упал после записи в Redis, до `COMMIT` | События будут применены повторно — guard по `tie_seq` делает это безопасным; водяной знак в Redis при этом больше, чем в PG, что допустимо. |
| Нарушение порядка событий | Старое событие не перезапишет новое (guard). |
| Redis потерял данные | `STALE` или `NOMETA` → откат и пересборка сезона. |

**Водяной знак.** Задача — отличить плановый рестарт Redis (всё на месте, пересборка не нужна) от потери хвоста AOF, когда события уже удалены из outbox, а в Redis их нет.

- Каждая попытка обработки пачки получает `batch_id` из `outbox_batch_seq`. Последовательности не откатываются, поэтому номера попыток строго растут.
- Redis хранит в `meta` максимальный применённый `batch_id` — тем же атомарным скриптом, который делает `ZADD`.
- PG хранит в `worker_state.last_batch` номер последней **закоммиченной** пачки.
- Инвариант: `meta.batch >= worker_state.last_batch` ⇔ ничего не потеряно. При `appendfsync everysec` Redis теряет только суффикс AOF. Воркер один и работает последовательно, поэтому записи в AOF идут в порядке возрастания `batch_id`: всё после закоммиченной пачки `c` имеет номер больше `c`, всё до неё — меньше. Значит, максимум среди уцелевших записей не меньше `c` тогда и только тогда, когда запись пачки `c` уцелела, а вместе с ней и все более ранние.
- `meta.batch > last_batch` — нормальная ситуация: Redis применил пачку, а коммит в PG не прошёл. События остались в outbox и будут применены повторно, guard это допускает.
- Тот же механизм ловит failover на отстающую реплику Redis, причём независимо от того, насколько она отстала.
- Воркер проверяет инвариант при старте и периодически в простое (`findStaleSeasons`), а не только при обработке пачки: иначе после рестарта без новых событий чтения продолжали бы отдавать рейтинг без потерянного хвоста.

**Почему не `max(outbox.id)`.** Identity выделяется при вставке, а коммит происходит позже, поэтому событие с меньшим `id` может прийти после событий с большим. Пачка из одного такого запоздавшего события не сдвигает максимум, и её потеря в Redis осталась бы незамеченной.

**Почему один воркер.** При нескольких воркерах порядок записей в AOF перестаёт совпадать с порядком `batch_id`, и инвариант ломается. Масштабирование при необходимости — шардирование по `hash(player_id) % K`: у каждого шарда свой воркер, своя последовательность и свой водяной знак.

**Новый сезон.** У свежего сезона нет ни `meta`, ни закоммиченных пачек. Отсутствие `meta` при `expected = 0` — норма: терять нечего, скрипт сам создаёт `meta`. Поэтому `NOMETA` сигнализирует только о настоящей потере, а отдельный бутстрап сезона не нужен.

**Записи в обход outbox.** Правило «`expected = 0` ⇒ терять нечего» верно, только если в `player_scores` нельзя попасть иначе, чем через outbox. Seed через `COPY` это нарушает, поэтому **любая запись в обход outbox обязана завершаться `rebuild --force`**, а пересборка поднимает водяной знак. Кроме того, seed обязан продвинуть `tie_seq` (`setval`) за максимальное присвоенное значение: иначе последующие реальные события получат `tie_local` меньше seeded, и guard отбросит настоящее обновление как старое.

**Очистка.** Удаление строк после обработки порождает мёртвые строки, поэтому для `leaderboard_outbox` настроен агрессивный autovacuum (раздел 4.2). Альтернатива на будущее — партиционирование outbox по времени и `DROP` старых партиций.

**Пересборка (`npm run rebuild-leaderboard`)**

`src/lib/rebuild.ts`, на отдельном выделенном соединении:

1. Взять **эксклюзивный** сессионный `pg_advisory_lock(REBUILD_LOCK)`. Он дождётся текущей пачки воркера (у неё shared-lock), новые пачки не начнутся. Только после этого читать данные.
2. Под локом перепроверить инвариант: если `meta` есть и `meta.batch >= worker_state.last_batch` при `last_batch > 0`, пересборка не нужна. Флаг `--force` пропускает проверку и обязателен после seed.
3. `DEL leaderboard:{S}:rebuild` — убрать остатки прошлой упавшей попытки.
4. `INSERT INTO worker_state … ON CONFLICT DO NOTHING`; `W = nextval('outbox_batch_seq')`: пересборка — это ещё одна пачка со своим номером.
5. Читать партицию сезона пачками (keyset по `player_id`) и заливать во временный ключ конвейером `ZADD`.
6. Одним Lua-скриптом: `RENAME` временного ключа в рабочий (или `DEL` рабочего, если сезон пуст) и `HSET meta batch W`. Именно Lua: в `MULTI` ошибка одной команды не отменяет остальные.
7. `UPDATE worker_state SET last_batch = W`.
8. Отпустить lock. Воркер применяет накопившийся backlog; события, уже попавшие в снимок, отбрасывает guard по `tie_seq`.

Почему корректно: событие, удалённое из outbox, принадлежит пачке, закоммиченной до захвата lock, — значит, его UPSERT виден при чтении на шаге 5. События, закоммиченные позже, остаются в outbox, потому что воркер заблокирован. Пересборка ведёт себя как ещё одна пачка с номером `W`, поэтому доказательство инварианта распространяется и на неё. Если бы воркер только проверял lock без shared-блокировки, пачка, начатая до пересборки, могла бы записать новое значение в старый ключ, а `RENAME` затёр бы его устаревшим снимком.

Во время пересборки читатели видят старый ключ (или пустой ответ, если Redis был потерян), но не наполовину заполненный рейтинг.

**Рассмотренная альтернатива: `run_id` и окно переигрывания.** Вместо водяного знака можно хранить обработанные события ещё 10 минут (`processed_at` вместо `DELETE`), сравнивать `run_id` из `INFO server` с сохранённым в `meta` и при его смене переигрывать окно. Это проще объяснить и не требует отдельной последовательности, но механизм привязан к длине окна: он ловит только потерю свежее 10 минут. Failover на сильно отставшую реплику или рестарт после долгого простоя останутся незамеченными, и рейтинг молча станет неполным. Водяной знак сравнивает номера, а не время, поэтому ловит потерю любой давности; цена — одна последовательность, одна таблица и требование единственного воркера. Выбран водяной знак.

**Seed.** Загрузка через `COPY` идёт в обход outbox, поэтому после неё обязательны `rebuild --force` и `setval('tie_seq', …)` — см. «Записи в обход outbox».

**Чтения.** Активный сезон API держит в памяти (кеш `SELECT` из `seasons` с TTL ~1 с); на границе сезона чтения могут до секунды показывать старый сезон. Ключи используют hash tag (`leaderboard:{202609}`, `…:meta`, `…:rebuild`), чтобы в Redis Cluster ключи сезона лежали в одном слоте — это нужно для Lua-скриптов и `RENAME`.

### 4.5. Паттерн нагрузки

Смешанный с преобладанием чтения: ~1000 записей/с и ~10 000 чтений/с. Отсюда разделение: записи — в PG (надёжность), чтения — из Redis (скорость). PG практически не получает чтений.

### 4.6. Хватит ли одного инстанса

**PostgreSQL.** Для 1000 коротких транзакций в секунду одного инстанса достаточно, а чтений на PG почти нет, поэтому read-реплики для производительности не нужны. Реплика нужна для **отказоустойчивости**:

| Подход | Плюсы | Минусы |
|---|---|---|
| Асинхронная репликация + автоматический failover (Patroni) | Не замедляет запись | При failover можно потерять последние подтверждённые транзакции |
| Синхронная репликация | Подтверждённое не теряется | Каждая запись ждёт реплику, выше latency; при недоступности реплики запись блокируется (нужна вторая реплика) |
| Read-реплики для чтения | Разгружают primary | Лаг репликации; здесь не нужны, т.к. чтения идут из Redis |

Выбор для production: primary + синхронная реплика с кворумом из двух реплик или асинхронная с принятым риском. Масштабирование записи при росте на порядок — батчинг, затем шардирование по `player_id`.

**Redis.** Один инстанс держит ~1.5 ГБ данных и ~10 000 операций/с с запасом. Для отказоустойчивости — реплика и Sentinel. Чтения можно распределить на реплики ценой лага (рейтинг и так eventual). Redis Cluster на этом объёме не нужен: весь рейтинг сезона — один ключ, и шардировать его пришлось бы вручную.

## 5. API

Полная схема — `docs/openapi.yaml`; файл ведётся вручную и сверяется с кодом при изменении ручек.

| Метод | Путь | Ответы |
|---|---|---|
| POST | `/score` | `200 {player_id, season_id, score}`, `400` невалидное тело, `422` счёт вне пределов, `503` нет сезона или PG недоступен |
| GET | `/leaderboard/top?limit=100` | `200 {season_id, entries: [{rank, player_id, score}]}`, `400`, `503`; `limit` 1…1000 |
| GET | `/leaderboard/rank/{player_id}?n=5` | `200 {season_id, player: {...}, above: [...], below: [...]}`, `404`, `503`; `n` 0…50 |
| GET | `/health` | `200`/`503` с состоянием PG и Redis — единственная служебная ручка API |

Метрики отдаёт не API, а воркер, на своём порту (раздел 3.4).

Ошибки приложения — тело `{"error": "<код>"}`: `no_active_season`, `score_out_of_range`, `storage_unavailable`, `leaderboard_unavailable`, `player_not_ranked`. Ошибки валидации (`400`) формирует Fastify по JSON-схеме ручки, их тело — стандартное `{statusCode, error, message}`.

`score_delta` — целое, не равное нулю. Позиция считается с 1.

## 6. Оценка нагрузки и данных

Цифры — оценки, после seed они измеряются и заменяются в README.

### 6.1. Откуда взяты цифры

| Цифра | Источник | Смысл |
|---|---|---|
| 1000 записей/с | **Дано в ТЗ** («пиковые часы до 1000 обновлений в секунду») | Пиковая нагрузка на запись, под неё проектируем и тестируем |
| ~10 000 чтений/с | **Дано в ТЗ** («на порядок чаще, чем запись») | Пиковая нагрузка на чтение |
| 10 млн игроков | **Дано в ТЗ** (критерий оценки стоимости чтения) | **Размер данных**, а не нагрузка: элементы Sorted Set, строки партиции. RPS из этой цифры не выводится |

**10 млн — верхняя граница.** В рейтинг попадает только игрок, сыгравший хотя бы один матч в текущем сезоне. Если 10 млн — это все пользователи игры, реальный размер рейтинга будет меньше, и все оценки памяти и времени пересборки получаются с запасом.

**Сверка с реалистичной нагрузкой (предположение).** Если выводить нагрузку из аудитории: 10 млн пользователей → ~10% активны в день (1 млн) → ~5 матчей на игрока → ~5 млн обновлений в сутки ≈ 60/с в среднем, в пиковые часы ×3–5 ≈ 200–300/с. Это ниже пика из ТЗ в 3–5 раз: реалистичная нагрузка покрывается с запасом. Доля активных и число матчей — предположения, их стоит уточнить у продукта.

**Проверка на непротиворечивость.** Постоянные 1000 обновлений/с дали бы ~2.7 млрд обновлений за месяц, то есть ~270 матчей на каждого из 10 млн игроков. Поскольку 1000/с — пик, а не среднее, реальные объёмы outbox и WAL за месяц будут заметно ниже этой оценки.

### 6.2. Объёмы и рост

| Что | Сейчас (10 млн игроков) | При росте ×10 |
|---|---|---|
| Строк в `player_scores` за сезон | 10 млн, ~1–1.5 ГБ с PK | 100 млн, ~10–15 ГБ — партиция всё ещё приемлема |
| Redis | ~1.5 ГБ (~120–150 байт на игрока), с запасом на fork ~3 ГБ | ~15 ГБ в одном ключе: долгий rebuild и fork, нужно шардирование рейтинга |
| Записи | 1000/с — один PG справляется | 10 000/с — батчинг записи, шардирование PG, несколько воркеров по шардам |
| Чтения | 10 000/с — один Redis | 100 000/с — реплики Redis, микрокеш топа в API на ~1 с |
| Outbox | в стационарном режиме сотни строк: обработанные удаляются в той же транзакции. Растёт на ~1000 строк/с, пока доставка стоит | растёт на ~10 000 строк/с при простое доставки — партиционирование outbox по времени |
| История | партиция на сезон, ~1–1.5 ГБ в месяц | архив в холодное хранилище |

Хранимые данные по игроку: `player_id`, счёт, `tie_seq`, время обновления. Персональных данных нет.

## 7. Аудит и логирование

- **Формат:** JSON через `pino`, поля `request_id`, `route`, `status`, `duration_ms`.
- **Записи:** каждое начисление логируется на уровне `info`: `player_id`, `score_delta`, новый счёт, сезон. Это минимальный аудит «кто и сколько получил».
- **Чтения:** 10 000 запросов/с логировать полностью дорого — логируются ошибки и медленные запросы, остальное сэмплируется; метрики покрывают картину целиком.
- **Воркер и пересборка:** старт и финиш пересборки, срабатывание водяного знака (`STALE`, `NOMETA`), номер и размер пачки, ошибки Redis.
- **Хранение:** Loki/ELK с ретеншеном, например 14–30 дней.
- **Надёжный аудит** (если он нужен бизнесу, например для разбора жалоб) — отдельная append-only таблица `score_events`, партиционированная по дням. Объём до ~2.7 млрд строк в месяц — сотни ГБ, поэтому в задании не реализуется и описывается как компромисс.
