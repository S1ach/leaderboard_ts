# RFC-001: Сервис сезонного лидерборда

| Поле | Значение |
|---|---|
| Статус | Реализован (ревизия 3, учтены два раунда ревью) |
| Дата | 2026-09-16 |

---

## 1. Контекст и проблема

В игре есть сезонный рейтинг. После матча игрок получает очки, и они **прибавляются** к текущему счёту. Нужен сервис, который принимает изменения очков и отдаёт топ игроков, позицию игрока и его окружение в таблице.

Сезон длится месяц, после чего рейтинг начинается заново.

**Нагрузка (из ТЗ):**

- до 1000 обновлений очков в секунду в пиковые часы;
- чтений (top и rank) примерно в 10 раз больше, то есть порядка 10 000 RPS;
- до 10 млн игроков в сезоне.

**API:**

| Метод | Описание |
|---|---|
| `POST /score` | Тело `{"player_id": "...", "score_delta": 100}`. Прибавляет очки, возвращает новый счёт. |
| `GET /leaderboard/top?limit=100` | Топ-N игроков с очками. |
| `GET /leaderboard/rank/{player_id}?n=5` | Позиция игрока, сам игрок, N игроков выше и N ниже. |

**Правило сортировки:** по убыванию очков. При равенстве очков выше тот, кто **раньше** получил этот счёт (время последнего изменения очков). Позиция — порядковый номер с 1; благодаря tie-break двух игроков на одной позиции не бывает.

**Требование к надёжности:** данные переживают перезапуск сервиса.

## 2. Цели и не-цели

**Цели:**

- атомарное накопление очков без потерянных обновлений при конкурентных запросах;
- стабильный и одинаковый в обоих хранилищах порядок при равных очках;
- чтение top и rank за O(log N + M), без сортировки всех игроков на каждый запрос;
- отсутствие потери подтверждённых записей при падении любого одного компонента;
- восстановление read model из source of truth отдельной командой;
- stateless API, горизонтальное масштабирование через HPA;
- нагрузочные тесты с измеренными (а не предполагаемыми) результатами.

**Не-цели:**

- аутентификация и авторизация (`player_id` доверенный);
- frontend;
- автоматический сброс сезона в коде (описывается в разделе 8);
- брокеры сообщений (Kafka, RabbitMQ), CDC, микросервисы;
- реализация нескольких архитектур (рассматриваются в разделе 4, реализуется одна).

## 3. Оценка объёмов

Все цифры ниже — **оценки** для выбора решения. Измеренные значения — в README.

| Что | Оценка | Как получена |
|---|---|---|
| Строк в `player_scores` за сезон | до 10 млн | по ТЗ |
| Размер `player_scores` + PK | порядка 1–1.5 ГБ | ~100 байт на строку с заголовком + индекс |
| Событий outbox за сезон | до ~2.7 млрд | 1000/с × 86 400 × 31 |
| Размер outbox в стационарном режиме | небольшой | события удаляются после обработки |
| Redis Sorted Set на 10 млн игроков | порядка 1.5 ГБ | ~120–150 байт на элемент при `player_id` ~32 символа (skiplist + dict + строка) |
| Память Redis с запасом | ~3 ГБ | запас на copy-on-write при сохранении RDB/AOF rewrite |

Вывод: весь рейтинг сезона помещается в память одного инстанса Redis, а записи укладываются в возможности одного инстанса PostgreSQL. Шардирование на этом масштабе не требуется.

## 4. Рассмотренные варианты

### Вариант A. Только PostgreSQL

Индекс `(season_id, score DESC, tie_seq ASC)`. Top — index scan первых N строк, дёшево. Rank — `COUNT(*)` игроков выше, это O(позиция): для игрока в середине рейтинга придётся пройти миллионы записей индекса на каждый запрос. При 10 000 RPS это не работает. Можно пересчитывать позиции периодически, но тогда rank устаревает на период пересчёта.

### Вариант B. Только Redis (Sorted Set + AOF)

Самый быстрый и простой. Но при `appendfsync everysec` при падении теряется до ~1 секунды подтверждённых записей, а `appendfsync always` сильно снижает пропускную способность. Нет реляционного хранилища для истории, аналитики и архива сезонов. Объём данных ограничен памятью.

### Вариант C. PostgreSQL + Redis, dual write в обработчике запроса

API пишет в PG, затем в Redis. Если запись в PG прошла, а в Redis — нет (сеть, падение процесса между шагами), хранилища расходятся навсегда до ручного вмешательства. Порядок двух конкурентных записей в Redis может отличаться от порядка в PG.

### Вариант D. PostgreSQL + transactional outbox + Redis (выбран)

В одной транзакции PG обновляется счёт и пишется событие в outbox. Отдельный воркер переносит события в Redis. Чтения идут из Redis.

### Вариант E. PostgreSQL + CDC (logical replication / Debezium) + Redis

Надёжно, не требует outbox-таблицы, но добавляет Kafka Connect/Debezium или собственный потребитель logical replication. Для тестового задания это лишняя эксплуатационная сложность. Разумный следующий шаг, если outbox станет узким местом.

### Сравнение

| Критерий | A. Только PG | B. Только Redis | C. Dual write | **D. Outbox** | E. CDC |
|---|---|---|---|---|---|
| Consistency | строгая | строгая (одно хранилище) | возможна вечная рассинхронизация | eventual, лаг — миллисекунды, сходится гарантированно | eventual, сходится гарантированно |
| Надёжность | высокая | потеря до ~1 с при падении | потеря в Redis при частичном сбое | подтверждённое не теряется | подтверждённое не теряется |
| Чтение top | дёшево | O(log N + M) | O(log N + M) | O(log N + M) | O(log N + M) |
| Чтение rank | O(позиция), дорого | O(log N + M) | O(log N + M) | O(log N + M) | O(log N + M) |
| Запись | 1 UPSERT | 1 ZADD, самая быстрая | UPSERT + ZADD в запросе | UPSERT + INSERT в одной транзакции | UPSERT, WAL читается отдельно |
| Восстановление | не нужно | только из AOF/RDB | ручная сверка | rebuild из PG | rebuild из PG или replay |
| Компоненты | 2 (API, PG) | 2 (API, Redis) | 3 | 4 (API, воркер, PG, Redis) | 5+ |
| Сложность | низкая | низкая | низкая, но хрупкая | средняя | высокая |

**Почему D:** это единственный вариант из простых, который одновременно даёт O(log N) для rank, не теряет подтверждённые записи и гарантированно сходится после любых частичных сбоев. Цена — eventual consistency чтений и один дополнительный процесс (воркер).

## 5. Предлагаемое решение

### 5.1. Схема

```
          POST /score
               │
               ▼
┌──────────────────────────────┐
│ PostgreSQL (source of truth) │
│  BEGIN                       │
│   UPSERT player_scores       │
│   INSERT leaderboard_outbox  │
│  COMMIT                      │
└──────────────┬───────────────┘
               │ SELECT … FOR UPDATE SKIP LOCKED
               ▼
         outbox worker ──── Lua apply ────▶ Redis ZSET
                                           leaderboard:{season}
                                                 ▲
GET /leaderboard/top  ───────────────────────────┤
GET /leaderboard/rank ───────────────────────────┘
```

### 5.2. Модель данных PostgreSQL

См. `migrations/001_init.sql`. Ключевые решения:

- **Партиционирование `player_scores` по сезону.** Сброс сезона не требует `DELETE` миллионов строк: старая партиция отключается (`DETACH`) и архивируется или удаляется (`DROP`). PK включает ключ партиционирования, как того требует PostgreSQL.
- **Нет индекса по `(score, tie_seq)`.** Чтения идут из Redis, rebuild читает партицию целиком. Такой индекс удорожал бы каждое обновление: изменение индексированной колонки исключает HOT update, что увеличивает WAL и bloat. `fillfactor = 85` оставляет место на странице для HOT update.
- **`version` не нужна.** Её роль выполняет `tie_seq`: он монотонно растёт при каждом изменении очков игрока.
- **`season_id` — integer** (`202609`), а не строка: компактнее в строке и индексе.
- **Сезоны не пересекаются** — это гарантирует `EXCLUDE`-ограничение. Без него CTE выбора сезона при пересечении вернул бы две строки, и UPSERT выполнился бы дважды.
- **`tie_seq` с `CACHE 1`.** При `CACHE > 1` каждое соединение заранее резервирует свой диапазон значений, и порядок между сессиями перестаёт соответствовать времени.
- **`worker_state`** хранит водяной знак для обнаружения потери данных в Redis (раздел 5.5).

### 5.3. Запись: атомарное накопление

Один запрос, одна транзакция, один round trip (`src/lib/score.ts`):

```sql
WITH s AS (
  SELECT id FROM seasons
  WHERE starts_at <= now() AND now() < ends_at
),
upsert AS (
  INSERT INTO player_scores (season_id, player_id, score, tie_seq)
  SELECT s.id, $1, $2, nextval('tie_seq') FROM s
  ON CONFLICT (season_id, player_id) DO UPDATE
    SET score      = player_scores.score + EXCLUDED.score,
        tie_seq    = EXCLUDED.tie_seq,
        updated_at = now()
  RETURNING season_id, player_id, score, tie_seq
)
INSERT INTO leaderboard_outbox (season_id, player_id, score, tie_seq)
SELECT season_id, player_id, score, tie_seq FROM upsert
RETURNING season_id, score;
```

Почему это корректно при конкурентных запросах: при конфликте `ON CONFLICT DO UPDATE` блокирует строку. Вторая транзакция ждёт, затем перечитывает актуальную версию строки и прибавляет дельту к уже обновлённому значению. Lost update не возникает, явный `SELECT … FOR UPDATE` не нужен. Это проверяется интеграционным тестом: K параллельных запросов по +1 дают ровно +K.

Сезон определяется временем транзакции в БД, а не часами API-пода, поэтому матч, закрытый в 23:59:59, не попадёт в другой сезон из-за рассинхронизации часов. Если активного сезона нет, запрос возвращает ошибку.

Outbox содержит **абсолютное** состояние (`score`, `tie_seq`), а не дельту. Поэтому повторное применение события безопасно.

Валидация: `player_id` — непустая строка ограниченной длины; `score_delta` — целое, не равное нулю (иначе игрок без изменения очков потерял бы место среди равных).

Коды ошибок: если итоговый счёт нарушает `CHECK` (раздел 5.4), PG возвращает `check_violation`, API отвечает `422`, транзакция откатывается целиком (outbox не затрагивается). Если активного сезона нет — `503`.

### 5.4. Tie-break и кодирование в Redis

Sorted Set при равном score сортирует по имени элемента, то есть по `player_id`. Это не соответствует ТЗ, поэтому tie-break кодируется в сам score (double, целые точны до 2^53):

```
tie_local   = tie_seq - season.tie_base            -- 0 … 2^32-1
redis_score = score * 2^32 + (2^32 - 1 - tie_local)
```

`ZRANGE … REV` отдаёт элементы по убыванию: сначала больше очков, при равных очках — меньший `tie_local`, то есть кто раньше получил этот счёт. Декодирование:

```
score     = floor(redis_score / 2^32)
tie_local = 2^32 - 1 - (redis_score - score * 2^32)
```

Ограничения:

- `tie_local < 2^32 ≈ 4.29 млрд` за сезон. При 1000 обновлений/с за 31 день — ~2.7 млрд, запас есть. Отсчёт идёт от `tie_base`, поэтому глобальную последовательность сбрасывать не нужно.
- `|score| < 2^21 ≈ 2.09 млн`. Проверяется `CHECK` в таблице. При других требованиях к очкам биты перераспределяются.
- `nextval()` не упорядочен по времени коммита: две параллельные транзакции могут закоммититься в обратном порядке. Для рейтинга это инверсия в пределах миллисекунд. Главное — PG и Redis сортируют по **одному и тому же** значению, поэтому rebuild воспроизводит тот же порядок.

### 5.5. Outbox worker

Работает **один активный воркер** (резервный экземпляр ждёт на `pg_try_advisory_lock` лидера). Почему один — см. «Водяной знак» ниже; для 1000 событий/с пачками по 500 это единицы вызовов Redis в секунду.

Lock лидера, shared-lock rebuild и транзакция пачки живут на **одном выделенном соединении**. Обрыв соединения означает потерю и lock, и незакоммиченной пачки: процесс завершается, оркестратор его перезапускает. Иначе старый лидер мог бы продолжить коммитить пачки одновременно с новым.

Цикл (`src/lib/outbox.ts`):

1. `BEGIN`
2. `pg_try_advisory_xact_lock_shared(REBUILD_LOCK)`. Если `false` — идёт rebuild: `ROLLBACK`, пауза, повтор.
3. `SELECT … FROM leaderboard_outbox ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED`
4. Схлопнуть пачку: для каждого игрока оставить событие с максимальным `tie_seq`.
5. `batch_id = nextval('outbox_batch_seq')`; для сезонов пачки `INSERT INTO worker_state … ON CONFLICT DO NOTHING`, затем прочитать `worker_state … FOR UPDATE` (`expected`).
6. Для каждого сезона — один вызов Lua-скрипта apply, который проверяет водяной знак и применяет события.
7. `DELETE` обработанных строк, `UPDATE worker_state SET last_batch = batch_id`, `COMMIT`.

Если Redis недоступен, транзакция откатывается, события остаются в outbox, воркер повторяет попытку с экспоненциальной задержкой. Если воркер упал между шагами 6 и 7, события будут применены повторно — это безопасно.

**Идемпотентность и порядок.** Скрипт применения (`APPLY_LUA` в `src/lib/redis.ts`) пишет значение, только если оно новее сохранённого: версия читается из самого score (`tie_local`), поэтому отдельный hash версий не нужен. Проверка водяного знака встроена в сам скрипт, а не сделана отдельным `EXISTS` перед пачкой, чтобы между проверкой и записью не было окна.

Ключи сезона используют hash tag (`leaderboard:{202609}`, `leaderboard:{202609}:meta`, `leaderboard:{202609}:rebuild`), чтобы в Redis Cluster они попадали в один слот — это нужно для Lua-скриптов и `RENAME`.

**Водяной знак.** Задача — отличить плановый рестарт Redis (всё на месте, rebuild не нужен) от потери хвоста AOF (события уже удалены из outbox, но в Redis их нет).

- Каждая попытка обработки пачки получает `batch_id` из последовательности. Последовательности не откатываются, поэтому номера попыток строго растут.
- Redis хранит в `meta` максимальный применённый `batch_id` (в том же атомарном скрипте, что и `ZADD`).
- PG хранит в `worker_state` номер последней **закоммиченной** пачки.
- Инвариант: `meta.batch >= worker_state.last_batch` ⇔ ничего не потеряно. При `appendfsync everysec` Redis теряет только суффикс AOF. Воркер один и работает последовательно, поэтому записи в AOF идут в порядке возрастания `batch_id`: все записи после закоммиченной пачки `c` имеют номер больше `c`, а до неё — меньше. Значит, максимум среди уцелевших записей не меньше `c` тогда и только тогда, когда запись пачки `c` уцелела (а вместе с ней и все более ранние).
- `meta.batch > last_batch` — нормальная ситуация: Redis применил пачку, а коммит в PG не прошёл. События остались в outbox и будут применены повторно, guard это допускает.
- Тот же механизм ловит failover на отстающую реплику Redis.
- Воркер проверяет инвариант при старте и периодически в простое, а не только при обработке пачки: иначе после рестарта без новых событий чтения отдавали бы рейтинг без потерянного хвоста.

**Новый сезон.** У свежего сезона нет ни `meta`, ни строки `worker_state`. Отсутствие `meta` при `expected = 0` — норма: ни одна пачка сезона не закоммичена, терять нечего, скрипт сам создаёт `meta`. Поэтому `NOMETA` сигнализирует только о настоящей потере.

**Записи в обход outbox.** Правило «`expected = 0` ⇒ терять нечего» верно, только если в `player_scores` нельзя попасть иначе, чем через outbox. Seed через `COPY` это нарушает. Поэтому **любая запись в обход outbox обязана завершаться `rebuild --force`**, а rebuild поднимает водяной знак. Кроме того, seed обязан продвинуть `tie_seq` (`setval`) за максимальное присвоенное значение: иначе последующие реальные события получат `tie_local` меньше seeded, и guard отбросит настоящее обновление как старое.

Почему не `max(outbox.id)`: identity выделяется при вставке, а коммит происходит позже. Событие с меньшим `id` может прийти после событий с большим. Пачка из одного такого «запоздавшего» события не сдвигает максимум, и её потеря в Redis не будет обнаружена.

Почему один воркер: при нескольких воркерах порядок записей в AOF перестаёт совпадать с порядком `batch_id`, и инвариант ломается. Масштабирование при необходимости — шардирование по `hash(player_id) % K`, у каждого шарда свой воркер, своя последовательность и свой водяной знак.

**Очистка.** Удаление после обработки порождает мёртвые строки, поэтому для `leaderboard_outbox` настроен агрессивный autovacuum. Альтернатива на будущее — партиционирование outbox по времени и `DROP` старых партиций.

**Метрики:** размер backlog, лаг (`now() - min(created_at)`), событий/с, ошибки Redis — `GET /metrics` воркера.

### 5.6. Чтение

- **Активный сезон для чтений.** API держит в памяти результат `SELECT id FROM seasons WHERE …` с TTL ~1 с. На границе сезона чтения могут до TTL показывать старый сезон — это зафиксированное ограничение.
- **Top:** `ZRANGE leaderboard:{season} 0 limit-1 REV WITHSCORES`, O(log N + M). `limit` ограничен (1000).
- **Rank:** один Lua-скрипт (`RANK_LUA`), чтобы позиция и соседи были из одного состояния. Сложность O(log N + M), где M ≤ 2N+1. `n` ограничен (50).

Если игрока нет в Redis, API возвращает `404` без обращения к PG. Игрок без событий по определению не в рейтинге, а окно, когда событие ещё не доставлено, составляет миллисекунды и клиентом не отличимо от «ещё не играл».

**Consistency для клиента:** `POST /score` возвращает новый счёт из PG, но `/rank` может ещё несколько миллисекунд показывать старое значение (лаг воркера). Клиент может показывать счёт из ответа POST.

## 6. Отказы и восстановление

| Сценарий | Поведение | Потеря данных |
|---|---|---|
| Падает PostgreSQL | `POST /score` возвращает 503. Чтения из Redis продолжают работать с последним состоянием. | Нет: неподтверждённые записи клиент повторяет. |
| Падает Redis | Чтения возвращают 503. Записи в PG продолжаются, outbox копится. | Нет: после восстановления воркер догоняет backlog. |
| Перезапуск API | Stateless, запросы уходят на другие поды. | Нет. |
| Падение воркера | Events копятся в outbox, растёт лаг чтений. Резервный экземпляр берёт lock лидера. | Нет. |
| Запись прошла только в PG | Событие в outbox, будет доставлено. | Нет. |
| Запись прошла только в Redis | Невозможно: в Redis пишется только то, что закоммичено в PG. | — |
| Плановый рестарт Redis, AOF цел | `meta.batch >= last_batch`, rebuild не запускается; недоставленное доедет из outbox. | Нет. |
| Рестарт Redis с потерей хвоста AOF | Скрипт apply или периодическая проверка возвращает `STALE` → rebuild. | Нет после rebuild. |
| Failover на отстающую реплику Redis | Аналогично: `STALE` → rebuild. | Нет после rebuild. |
| Очистка Redis (`FLUSHALL`, потеря ключа) | Нет `meta` → `NOMETA` → rebuild. | Нет после rebuild. |

**Настройки Redis:** `appendonly yes`, `appendfsync everysec`, `maxmemory` с запасом, `maxmemory-policy noeviction`. Молчаливое вытеснение элементов рейтинга хуже, чем явная ошибка записи. В docker-compose и k8s Redis нужен достаточный grace period при остановке: `SHUTDOWN`/`SIGTERM` делает fsync AOF, но `SIGKILL` по таймауту это обходит, и плановый рестарт превратится в потерю хвоста (которую водяной знак поймает, но ценой rebuild).

### Rebuild (`npm run rebuild-leaderboard`)

`src/lib/rebuild.ts`, на одном выделенном соединении:

1. Взять **эксклюзивный** сессионный `pg_advisory_lock(REBUILD_LOCK)`. Он ждёт завершения текущей пачки воркера (у неё shared-lock), новые пачки не стартуют. Только после этого начинать чтение.
2. Перепроверить инвариант: если `meta` есть и `meta.batch >= worker_state.last_batch` (при `last_batch > 0`), rebuild не нужен. Флаг `--force` пропускает проверку (нужен после seed).
3. `DEL leaderboard:{season}:rebuild` — удалить остатки прошлой упавшей попытки.
4. `INSERT INTO worker_state … ON CONFLICT DO NOTHING`; `W = nextval('outbox_batch_seq')`.
5. Прочитать партицию сезона пачками (keyset pagination по `player_id`), короткими транзакциями.
6. Залить во временный ключ через pipeline `ZADD`.
7. Одним Lua-скриптом: `RENAME` временного ключа в рабочий (или `DEL` рабочего, если сезон пуст) и `HSET meta batch W`.
8. `UPDATE worker_state SET last_batch = W`.
9. Отпустить lock. Воркер применяет накопленный backlog; события, уже учтённые в снимке, отбрасываются guard'ом по `tie_seq`.

Почему это корректно: любое событие, удалённое из outbox, принадлежит пачке, закоммиченной до получения lock, а значит, его UPSERT виден при чтении на шаге 5. События, закоммиченные позже, остаются в outbox, потому что воркер заблокирован. Rebuild ведёт себя как ещё одна пачка с номером `W`, поэтому доказательство инварианта распространяется и на него.

Во время rebuild читатели видят старый ключ (или пустой ответ, если Redis был потерян), без частично заполненного рейтинга.

## 7. Масштабирование

- **API stateless** — запускается N реплик за балансировщиком.
- **HPA для API:** старт по CPU (target 70%, minReplicas 2). Для production дополнительно RPS на под и p95 latency через Prometheus Adapter.
- **Воркер** не масштабируется HPA: активен один экземпляр (плюс резервный через leader lock), это требование водяного знака. Метрика backlog outbox используется для алертов. При росте нагрузки — шардирование по `hash(player_id)` с отдельным воркером и водяным знаком на шард.
- **Соединения к PG:** `реплики × размер пула` не должно превышать `max_connections`; при росте числа подов — PgBouncer.
- **HPA не масштабирует хранилища.** Чтения Redis масштабируются репликами (с учётом лага репликации), записи PG — вертикально.

## 8. Сезоны

- Таблица `seasons` задаёт границы; активный сезон определяется временем транзакции.
- Партиция, строка в `seasons` (с `tie_base = текущее значение tie_seq`) и строка `worker_state` создаются **заранее** функцией `create_season()` (`npm run create-season -- 202610`), в production — плановой задачей.
- В момент смены сезона записи начинают попадать в новую партицию, событие → новый ключ `leaderboard:{new_season}`. Никаких массовых `DELETE`.
- Старый сезон: ключ Redis удаляется через `UNLINK` спустя период хранения, партиция отключается и удаляется или переносится в холодное хранилище.

## 9. Тестирование

Интеграционные тесты (`test/`): конкурентное накопление, tie-break, идемпотентность, порядок, эквивалентность rebuild и штатной доставки, недоступный Redis, водяной знак (`STALE`, `NOMETA`, плановый рестарт), seed в обход outbox, блокировка воркера на время rebuild.

Нагрузочные тесты (`k6/`, executor `constant-arrival-rate`): write (1000 `POST /score`/с), read (top и rank, 10 000 RPS), mixed (10 чтений : 1 запись). Результаты — в README.

## 10. Риски

- **Повторные `POST /score` от клиента** (таймаут и retry) удвоят очки: API сам по себе не идемпотентен, в теле нет `match_id`. Решение — `Idempotency-Key` / `match_id` с уникальным индексом. Известное ограничение.
- **Лаг outbox** при длительной недоступности Redis растёт; чтения показывают устаревший рейтинг.
- **Bloat outbox** при неверной настройке autovacuum.
- **Память Redis** при росте числа игроков сверх оценки; без `noeviction` возможна тихая потеря данных.
- **Ограничения кодирования** score и `tie_local` (раздел 5.4).
- **Один активный воркер** — ограничение пропускной способности доставки и время переключения на резервный экземпляр.
- **Rebuild на 10 млн игроков** занимает время, в течение которого чтения отстают.

## 11. Открытые вопросы и принятые допущения

1. Отрицательные `score_delta` **допускаются**, итоговый счёт может быть отрицательным (допущение; кодирование и guard это поддерживают).
2. Максимальный счёт за сезон — 2^21 (допущение; при других требованиях биты перераспределяются).
3. `player_id` — непустая строка до 128 символов (допущение, настраивается).
4. `/rank` для игрока не в рейтинге — `404` без похода в PG.
5. При недоступном Redis чтения возвращают `503`.
6. Чтения прошлых сезонов через этот API не реализованы.
