## Стенд

Во время серии на 10 млн хост был занят посторонними приложениями (load average 6–10) — оценка по ходу прогонов, **сырые данные не сохранены**.

## Как повторить

Данные заливаются `npm run seed -- --players N`, затем:

```bash
docker run --rm -i --add-host=host.docker.internal:host-gateway -v ./k6:/scripts \
  -e BASE_URL=http://host.docker.internal:3000 -e PLAYERS=1000000 -e DURATION=30s -e MAX_VUS=2000 \
  grafana/k6:0.54.0 run --summary-export=/scripts/results/mixed-1m.json /scripts/mixed.js \
  | tee k6/results/mixed-1m.txt
k6/sample-lag.sh > k6/results/mixed-1m-lag.txt   # параллельно, в другом терминале
```

Переменные сценариев: `BASE_URL` (несколько адресов через запятую — так снят прогон с двумя инстансами), `PLAYERS` (диапазон id, должен быть не больше числа игроков в seed), `DURATION`, `RATE` для `write.js` и `read.js`, `WRITE_RATE` для `mixed.js` (чтения идут по `5 × WRITE_RATE` на top и rank), `MAX_VUS`. Скрипты `npm run k6:*` пробрасывают `PLAYERS`, `DURATION`, `RATE`, `WRITE_RATE` и `MAX_VUS` из окружения; все три сценария с сохранением отчётов и лага запускает `k6/run-all.sh`. Скрипт `k6/sample-lag.sh` **восстановлен по формату записанных файлов, исходный не сохранился**.

## Как читать цифры

При чтении таблиц важно помнить: при `constant-arrival-rate` k6 запускает итерации с заданной частотой, и если свободных виртуальных пользователей нет, итерация **отбрасывается** (`dropped_iterations`) и в задержки не попадает. Поэтому заметный dropped означает, что целевая нагрузка не достигнута, а p95 и p99 занижены — самые медленные моменты частично не измерены.

**Что из этого следует.**

- На 100 тыс. и 1 млн цели ТЗ (1000 записей/с и 10 000 чтений/с) достигнуты: dropped не больше 0.3 %, кроме `mixed-100k` с 2.4 %.
- Второй инстанс API на 1 млн снизил p95 смешанного сценария с 8.4 до 4.9 мс при той же нагрузке — по одному прогону каждого варианта.
- **На 10 млн смешанный сценарий ни разу не набрал целевые 11 тыс. RPS** (dropped 11–19 %). Его p95 искажён отброшенными запросами, и утверждать по нему, что сервис держит такую нагрузку, нельзя.
- Из чтений на 10 млн run1 цель не достиг, run3 дал p95 21.6 мс, но при `MAX_VUS` 600: ограничение заставляет k6 отбрасывать запросы вместо ожидания, поэтому цифра занижена и с прогонами на 2000 напрямую не сравнима.
- **Гипотеза, не доказано:** хвост задержек на 10 млн создаёт генератор в той же машине, а не путь данных. В пользу неё ручные замеры без нагрузки: `rank` медиана 0.90 / p95 2.0 мс, `top` 0.88 / 1.3 мс; `INFO commandstats` — `ZREVRANK` 12.7 мкс, `ZRANGE` 8.1 мкс, скрипт rank 36.7 мкс (**сырые данные не сохранены**). Проверяется только генератором на отдельной машине — **не измерено**.
- **Гипотеза, не доказано:** высокий p95 в run1 чтений совпал с autovacuum только что залитой партиции (наблюдение по `pg_stat_user_tables`, **сырые данные не сохранены**).
