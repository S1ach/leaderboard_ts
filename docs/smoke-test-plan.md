# План smoke-тестирования бизнес-процессов

Цель: проверить сквозной путь HTTP → PostgreSQL/outbox → отдельный worker → Redis → HTTP и все реализованные ручки. Контракт: `docs/openapi.yaml`, фактические маршруты: `src/api/app.ts`, `src/worker/runner.ts`.

## Стенд и данные

Отдельный Docker Compose project `lb-smoke`, собственные volumes и порты: API 13000, metrics 19100, PostgreSQL 15433, Redis 16380. Исходный проект `leaderboard_ts` не изменяется. Для прогона нужны Docker и Node.js ≥22; команды выполняются из корня репозитория. Начальное состояние — новые volumes с миграциями и пустым текущим сезоном.

Скрипт изменяет только тестовые данные, останавливает сервисы **lb-smoke**, очищает его Redis и меняет даты тестовых сезонов. Не применять к рабочему окружению. Сценарии последовательные: сбои записываются, остальные группы продолжают выполняться; итоговый код ненулевой при любом FAIL. Ошибка начального состояния останавливает прогон. Остановленное хранилище запускается в `finally`.

## Матрица бизнес-процессов

| № | Процесс и действия | Ожидаемый результат |
|---|---|---|

| 02 | Alice +100, Bob +100, Carol +50, negative −5; Alice +50 и −50 | Накопление; отрицательный счёт; при равенстве раньше набравший выше; обновление меняет порядок среди равных |
| 02 | Top с limit=1/1000/по умолчанию; rank с n=0/1/50/по умолчанию; первый и последний игрок | Ограничение числа записей; правильные ранги и соседи; обрезание на краях; n=0 без соседей |

| 04 | Id длиной 128 и Unicode с URL-спецсимволами | Запись и последующее чтение того же id |
| 05 | ±2097151, затем выход за верхнюю/нижнюю границу | 200 на границе, 422 `score_out_of_range` при переполнении; прежний счёт в PostgreSQL и Redis |
| 06 | Метрики воркера после доставки | 200, все 8 метрик, worker_is_leader=1, outbox_backlog=0 |
| 07 | Остановить worker, начислить, прочитать, запустить worker | Запись принята, outbox непустой, до доставки rank=404; после запуска появляются очки |
| 08 | Остановить Redis; health/ready/top/rank/score; восстановить Redis | Health=200; ready=503 с redis=false; чтения=503 `leaderboard_unavailable`; запись=200; после восстановления запись доставлена |
| 09 | Прогреть кеш сезона, остановить PostgreSQL, дождаться TTL; чтения/запись/пробы; восстановить | Чтения и health=200; ready=503 с postgres=false; запись=503 `storage_unavailable`; после восстановления запись и доставка работают |

## Покрытие ручек

| Метод и путь | Ответы, проверяемые по HTTP |
|---|---|
| POST /score | 200, 400, 422, 503 (нет сезона, недоступен PostgreSQL) |
| GET /leaderboard/top | 200, 400, 503 (нет сезона, недоступен Redis) |
| GET /leaderboard/rank/{player_id} | 200, 400, 404, 503 (нет сезона, недоступен Redis) |
| GET /health | 200 в штатном режиме и при отказах хранилищ |
| GET /ready | 200; 503 при отказе каждого хранилища |
| GET /metrics (worker) | 200 и значения/наличие метрик |

Eventual consistency учитывается polling-проверками состояния с бюджетом 25 секунд и паузой 200 мс; таймаут одного HTTP-запроса 15 секунд. Это предел ожидания теста, не измерение SLA. Каждая полученная HTTP-ответная запись, в том числе промежуточные ответы polling, сохраняется в JSON.

## Запуск

```bash
docker compose --env-file scripts/smoke.env -p lb-smoke up -d --build
node scripts/smoke.mjs
```

Результаты: `docs/smoke-results.json` — время прогона, статусы сценариев, URL, метод, отправленное тело, ожидаемый и фактический код, время и тело ответа. Для повторного прогона нужны новые volumes: после сохранения результатов удалить только тестовый стенд следующей командой и вновь выполнить запуск.

```bash
docker compose --env-file scripts/smoke.env -p lb-smoke down -v
```

Дополнительная регрессия использует отдельную БД `leaderboard_test` и Redis DB 1 того же smoke-стенда, пока fault-сценарии не выполняются:

```bash
POSTGRES_PORT=15433 REDIS_PORT=16380 npm test
npm run typecheck
```

## Критерий и границы

Smoke считается успешным, если все 12 сценариев завершились PASS, проверены все 6 ручек, после сбоев запись/чтение восстановились и подтверждённые очки сохранились. Сверка значений и порядка обязательна: одного кода 200 недостаточно.

За пределами smoke: нагрузочный SLA 1000/10000 RPS, 10 млн игроков, Kubernetes/HPA, авторизация (не реализована), исчерпание tie_seq, полный JSON Schema conformance, реальное ожидание календарной границы, аварийный SIGKILL/AOF-tail. Смена сезона моделируется SQL-изменением времени только в тестовой БД. Холодный кеш при отказе PostgreSQL, повторная/устаревшая доставка покрываются дополнительными существующими интеграционными тестами, а не этим HTTP-прогоном.
