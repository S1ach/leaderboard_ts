## SMOKE-01 — высокий приоритет: рейтинг расходился с PostgreSQL при конкуренции. Исправлено

**Воспроизведение:** на пустом стенде после базовых начислений отправить 20 одновременных `POST /score` с `{"player_id":"parallel","score_delta":1}`. Дождаться доставки, читать `/leaderboard/rank/parallel?n=1`.

**Ожидание:** все начисления приняты; PostgreSQL, top и rank в итоге показывают 20.

**Факт первого прогона:** ответы POST дали весь набор итогов 1…20; rank более 25 секунд показывал **17**. Диагностический SQL после сбоя:

```text
SELECT player_id,score,tie_seq FROM player_scores WHERE player_id='parallel';
parallel|20|18
SELECT count(*) FROM leaderboard_outbox;
0
```

Outbox уже пуст, то есть это не отставание доставки, а устойчивое расхождение. Данные — в [smoke-first-failure.json](smoke-first-failure.json).

**Причина.** `src/lib/score.ts` брал `nextval('tie_seq')` в ветке INSERT, то есть **до** ожидания блокировки строки, а в ветке UPDATE переносил это значение через `EXCLUDED.tie_seq`. При конкурентных начислениях порядок выданных номеров не совпадает с порядком, в котором обновления реально применились к строке. `collapse()` в `src/lib/outbox.ts` и Lua-guard в `src/lib/redis.ts` считают больший `tie_seq` более новым состоянием, поэтому в Redis оставался промежуточный счёт, а все события удалялись из outbox как обработанные. Водяной знак такое расхождение не ловит: он сравнивает номера пачек, а не содержимое.

**Исправление.** В ветке `DO UPDATE` номер берётся заново: `tie_seq = nextval('tie_seq')`. Это выражение вычисляется уже после захвата блокировки строки, поэтому номера версий растут в том же порядке, в котором обновления применяются. RFC 4.4 обновлён.

**Побочный эффект.** При конфликте расходуются два значения последовательности вместо одного (одно — в отменённой попытке вставки). Запас `tie_local` на сезон уменьшается с 4.29 млрд до примерно 2.1 млрд начислений; это отражено в README, RFC 2.2 и `docs/operations.md`.

**Регрессионный тест:** `test/concurrency-order.test.ts` — три круга по 30 одновременных начислений; проверяется, что событие с максимальным `tie_seq` несёт итоговый счёт, и что после доставки rank показывает тот же счёт, что и PostgreSQL. На коде до исправления тест падает на первом же круге.

## SMOKE-02 — средний приоритет: разрешённый ID нельзя было прочитать через rank. Исправлено

Контракт допускает `player_id` длиной 1–128 символов. Маршрут rank отвечал `414` (`FST_ERR_MAX_PARAM_LENGTH`) до валидации по схеме.

| Длина / значение | POST /score | GET rank, до | GET rank, после |
|---|---|---|---|
| 100 ASCII-символов | 200 | 200 | 200 |
| 101 ASCII-символ | 200 | **414** | 200 |
| 128 ASCII-символов | 200 | **414** | 200 |
| 129 ASCII-символов | 400 | **414** | **400** (по контракту) |
| `игрок /?#😀` (URL-encoded) | 200 | 200 | 200 |

**Причина.** У роутера Fastify лимит длины path-параметра по умолчанию — 100 символов, и он сравнивается с **URL-закодированной** длиной. Один символ `player_id` в кодировке занимает до 12 символов (`%XX` на каждый байт UTF-8), поэтому допустимый id из 128 символов с эмодзи занимает в URL более 700 символов.

**Исправление.** `routerOptions: { maxParamLength: PLAYER_ID_MAX_LEN * 12 }` в `src/api/app.ts`. Лимит роутера заведомо выше контрактного, а настоящее ограничение в 128 символов проверяет схема ручки и отвечает `400`, как описано в OpenAPI.

**Регрессионные тесты:** в `test/api.test.ts` — приём и чтение id из 128 ASCII-символов и id из 128 UTF-16 единиц с кириллицей, пробелом, URL-спецсимволами и эмодзи (751 символ после кодирования), а также `400` на 129 символов и при записи, и при чтении.

## Повторение

План и команды: [smoke-test-plan.md](smoke-test-plan.md). Основной скрипт: [../scripts/smoke.mjs](../scripts/smoke.mjs).

```bash
docker compose --env-file scripts/smoke.env -p lb-smoke down -v     # нужны чистые volumes
docker compose --env-file scripts/smoke.env -p lb-smoke up -d --build --wait
node scripts/smoke.mjs
node scripts/smoke-player-id.mjs      # дополнительные границы player_id
```

Дополнительный скрипт сделан повторяемым: ожидаемый счёт в GET сверяется с тем, что вернул предыдущий POST, поэтому чистый набор id ему больше не нужен.

## Ограничения прогона

Нагрузочные характеристики и production-готовность этим прогоном не подтверждались: пределы 1000 записей/с и 10 000 чтений/с, 10 млн игроков, Kubernetes и HPA остаются за рамками. Смена сезона моделировалась изменением дат в изолированной БД, а не ожиданием календарной границы. Аварийная остановка (`SIGKILL`) и реальная потеря хвоста AOF не проверялись. Успешные существующие тесты не исключали найденных HTTP-дефектов: оба нашлись только сквозным прогоном через HTTP, поэтому оба теперь закрыты автотестами.
